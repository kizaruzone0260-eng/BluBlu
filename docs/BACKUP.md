# Бэкап и восстановление

Один экран, который раньше был размазан по `DEPLOY.md`, `HARDENING.md` и `PROGRESS.md`.

## Что есть в репозитории

| Файл | Что делает |
|---|---|
| `deploy/scripts/backup.sh` | ежедневный дамп: `pg_dump` (compose или напрямую), при отсутствии `pg_dump` — `apps/api/scripts/logical-backup.mjs`; тар файлов хранилища; ротация `KEEP_DAYS` (7 по умолчанию). **Без `BACKUP_PASSPHRASE` скрипт отказывается работать** (часть D1, 2026-10-16): открытые дампы всей школы он больше не оставляет, уже записанное удаляется |
| `deploy/scripts/restore.sh` | расшифровка (если нужно) → `psql` с `ON_ERROR_STOP=1` или логическое восстановление из `*-logical.tar.gz`. Переменные, не позиционные аргументы: `BACKUP=… FILES_BACKUP=… BACKUP_PASSPHRASE=… PGDATABASE=… STORAGE_DIR=…` |
| `deploy/scripts/test-backup-restore.sh` | **цикл целиком на настоящих скриптах** (часть D2): миграции журнала → сид → backup в трёх режимах (отказ без пароля / открытый по `ALLOW_UNENCRYPTED_BACKUP=1` / шифрованный) → restore в пустую базу → сверка счётчиков, позы RLS, значения jsonb и байтов файла. Зависит только от `psql`, `pg_dump`, `openssl` |
| `apps/api/scripts/logical-backup.mjs` | дамп/ресторе через драйвер: таблицы берутся из `pg_class` (новую вручную дописывать не надо), порядок FK — `session_replication_role='replica'` с тихим пропуском при непривилегированной роли, миграции применяются самим рестором |
| Шифрование | `openssl enc -aes-256-cbc -pbkdf2 -salt`, оригинал после шифрования удаляется. Ветка шифрования берёт **все** файлы прогона по метке времени — раньше glob `*-"$метка".*` пропускал логический дамп `klass-<метка>-logical.tar.gz`, и скрипт писал «encrypted», оставаясь открытый слепок базы рядом (нашло это теста цикла, а не ревью) |

**Проверено тестом** `apps/api/test/integration/phase1-backup.test.ts`: дамп → шифрование →
неверная фраза НЕ восстанавливает → верная фраза даёт побайтовое совпадение → восстановление в
новую пустую базу → сверка счётников всех базовых таблиц и конкретного засеянного ряда.

**Проверено прогоном самих скриптов** (часть D2, 2026-10-16): job `backup-restore` в CI
(Postgres 16 как сервис, `pg_dump`/`psql` есть) и локально на переносном Postgres в логическом
режиме (клиентских утилит там нет, и это ровно та ветка, которая остаётся запасной). Локальный
прогон дал: отказ без пароля и пустой каталог после него; открытые файлы при
`ALLOW_UNENCRYPTED_BACKUP=1`; только `.enc` при пароле (заголовок `53 61`, а не gzip-`1f 8b`);
восстановление в пустую базу; счётчики `users=2, classes=1, class_members=1, posts=1`,
`relrowsecurity=false` у 0 таблиц, привилегий у `anon`/`authenticated` — 0, метка enum `sending`
доехала; байт файла хранилища совпал.

## Настройки

```
BACKUP_DIR=/var/backups/klass         # куда писать архивы (по умолчанию <репозиторий>/backups)
STORAGE_DIR=/srv/klass/files          # каталог вложений, который тарится вместе с базой
KEEP_DAYS=7                           # ротация: файлы старше N дней удаляются из BACKUP_DIR
BACKUP_PASSPHRASE=…                   # обязателен: без него скрипт отказывается (D1)
ALLOW_UNENCRYPTED_BACKUP=1            # ТОЛЬКО для учебных прогонов: пишет открытый текст,
                                      # с громким предупреждением в stderr
```

`BACKUP_PASSPHRASE` — единственное, что отделяет читаемый дамп всей школы (почта, имена, тексты
чата и заметок) от зашифрованного архива. Фраза не хранится в репозитории и не выводится в логи;
потерять её = потерять резервные копии.

Где ей жить: в менеджере паролей владельца (рядом с записью сервера), и один раз — в файле на
самом сервере с правами `600`, вне веб-каталога и вне `BACKUP_DIR` (иначе копия пароля уедет
вместе с копией дампа). В `cloud.env` и в git её нет и быть не должно.

## Cron на сервере

```
17 3 * * * klass BACKUP_PASSPHRASE=… /srv/klass/deploy/scripts/backup.sh >> /var/log/klass-backup.log 2>&1
```

В `render.yaml` cron-задачи нет: бэкап существует ровно настолько, насколько он поставлен на
сервере. Ротация `KEEP_DAYS` живёт внутри того же каталога, поэтому «копии есть» ≠ «копии в
разных местах» — см. следующий раздел.

## Куда класть копии (правило 3-2-1 в минимальной версии)

1. **На сервере** — `BACKUP_DIR`, 7 дней (это не копия, это карман: при смерти диска он
   умирает вместе с данными).
2. **Вне сервера, автоматически** — любой ящик, к которому у сервера есть ключ без пароля в
   коде: `restic`/`borg` в S3-совместимое хранилище, либо `rclone copy` в бесплатный
   object storage, либо второй VPS по `rsync -e ssh`. Кладётся `.enc`, а не открытый дамп.
3. **Вне ящика, вручную раз в месяц** — второй конец: домашний компьютер или съёмный диск,
   и там же — распечатанная/менеджером хранимая фраза.

Проверка, что копия настоящая: `openssl enc -d … | gzip -t` на файле, скачанном из второго
места, а не из первого.

## Ежемесячная проверка восстановления (30 минут, не «когда-нибудь»)

Раз в месяц, в календарь владельцу, — ровно то, что автоматизирует job `backup-restore`:

```
createdb klass_restore_test
BACKUP_PASSPHRASE=… PGDATABASE=klass_restore_test \
  BACKUP=/path/klass-<stamp>.sql.gz.enc FILES_BACKUP=/path/klass-files-<stamp>.tar.gz.enc \
  STORAGE_DIR=/tmp/restore-check/files \
  bash deploy/scripts/restore.sh
```

После чего посмотреть глазами четыре числа и две позы:

```
select count(*) from users; select count(*) from classes;
select count(*) from class_members; select count(*) from notifications;
-- поза RLS: ни одной таблицы без relrowsecurity и ни одной привилегии у anon/authenticated
select count(*) from pg_class k join pg_namespace n on n.oid = k.relnamespace
 where n.nspname = 'public' and k.relkind = 'r' and k.relrowsecurity = false;
select count(*) from information_schema.role_table_grants
 where grantee in ('anon','authenticated');
```

Все четыре счётчика обязаны совпасть с продакшном (снимок снимается перед прогоном), а две позы
— дать ноль. Плюс открыть один материал в восстановленной базе под допустимым логином и убедиться,
что файл на месте: база без хранилища восстанавливается молча и неполно.

## Supabase: шаги для владельца

`pg_dump` и `psql` на Supabase работают через connection string пула, но выполнять их должен
владелец со своей машины — у агента ни доступа, ни клиента:

1. Дамп:
   `pg_dump "postgres://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:6543/postgres" | gzip -9 > klass-$(date +%Y%m%d).sql.gz`
   (порт 6543 — пулер; для `pg_dump` лучше прямой 5432, если он разрешён).
2. Шифрование той же командой, что в `backup.sh`:
   `openssl enc -aes-256-cbc -pbkdf2 -salt -in klass-<stamp>.sql.gz -out klass-<stamp>.sql.gz.enc -pass pass:"$BACKUP_PASSPHRASE"`.
3. Проверка расшифровки вслепую: `openssl enc -d … | gzip -t` — должно вернуть 0.
4. Тренировочное восстановление в **отдельную пустую базу** (не в продакшн): `createdb`
   → `restore.sh` → сверки из списка выше.
5. Отдельно проверить, что восстановленная база не отдаёт данные по `anon`/`authenticated`
   (тот же аудит, что делает `pnpm db:audit -- cloud.env`), потому что ресторе через
   сервис-роль политики не пересоздаёт, а переносит.

Живого `pg_dump`-бэкапа и восстановления на Supabase в этом отчёте нет: это действие владельца,
и оно не может быть доказано офлайн.

## Проверить на сервере после деплоя f7b2222 (2026-10-17)

До этой правки `restore.sh` расшифровывал архив В ТОТ ЖЕ каталог (`klass-….sql.gz.enc` →
`klass-….sql.gz`) и не убирал результат: каждое восстановление оставляло на диске открытую копию
всей базы рядом с зашифрованным бэкапом. Если `restore.sh` на сервере запускался хоть раз, эти
файлы там могли остаться. Раз в месяц (и сразу после этого деплоя):

```bash
find /opt/klass/deploy/backups -type f \( -name '*.sql.gz' -o -name '*files-*.tar.gz' \) -printf '%p %s\n'
```

Пустой вывод — открыто́го ничего нет. Найденное сначала сверить с `.enc`-парой (`sha256sum` после
`openssl enc -d` того же архива), потом удалить: это копии всей базы, и лежать им негде.
`backup.sh` открытые файлы не оставляет — проверка «рядом с .enc лежат открытые файлы» есть в
цикле `pnpm test:backup` и в CI-джобе `backup-restore`.
