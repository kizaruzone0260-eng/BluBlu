# Решения по ходу работы

## 2026-10-07 (миграция 0021: снятие политик `app_trusted_access`)

- **Решение:** политики, добавленные `0020_rls_app_policies.sql`, удалены вперёд идущей
  миграцией `0021_rls_drop_app_policies.sql` (`DROP POLICY IF EXISTS app_trusted_access`
  по циклу over `pg_class` r/p в `public`). RLS **остаётся включённым** на всех таблицах,
  права не выдавались и не отзывались, ролей не создавалось, данных не касались.
- **Почему удалены, а не оставлены «на всякий случай»:** доказано каталогом, а не
  рассуждением (`apps/api/scripts/rls-audit.mjs`, read-only, секретов не печатает):
  - локальный/CI кластер (embedded Postgres и `postgres:16-alpine` с
    `POSTGRES_USER=klass` в `.github/workflows/ci.yml`): роль приложения `klass` —
    `rolsuper = true`, `rolbypassrls = true`, владелец 35/35 таблиц `public`,
    `relforcerowsecurity = 0` на всех;
  - бэкенд в бою (Supabase, Session pooler): роль приложения `postgres` — `rolsuper = false`,
    **`rolbypassrls = true`**, владелец 35/35 таблиц, `relforcerowsecurity = 0` на всех,
    и под ней видно `users_live = 1`, `classes = 4`, `lesson_sessions = 4`,
    `refresh_tokens = 28` (то есть `/api/me` и `/api/lessons/active` отвечали 200 всегда);
  - `anon`/`authenticated`: `has_table_privilege` = false по **всем** 35 таблицам
    (SELECT/INSERT/UPDATE/DELETE), чтение любой таблицы отказано на уровне привилегий,
    PostgREST с публичным ключом отвечает 401 на `users`, `classes`, `chat_messages`,
    `posts`, `files`, `teacher_notes`.
  Итог: политика `TO PUBLIC USING (true)` достижима только ролями, которые и так
  обходят RLS, а недостижима для тех, кого она «не должна открывать». Она не давала
  ничего — а ложное чувство, что «RLS теперь безопасен для не-владельца», только мешает.
- **Главный вывод инцидента:** `0020` не была причиной прод-боя видеоурка. Причина —
  Origin/CSRF-гейт, который отклонял собственный адрес страницы
  (`VIDEO_CALL_FINAL_FIX_REPORT.md`, фикс `896d355`).
- **Чем это рискуем и как закрыто:** если в будущем `DATABASE_URL` переведут на
  не-владелец без `BYPASSRLS`, policy-less RLS отфильтрует все SELECT в 0 строк →
  401 на `/api/me` → «выбрасывает на логин». Это теперь не сюрприз:
  `test/integration/phase1-rls-approle.test.ts` переписан (не удалён) и проверяет
  (1) инвариант «роль приложения = superuser/BYPASSRLS/владелец и ни одна таблица не
  FORCE», (2) отсутствие политик для `TO PUBLIC` на уровне `pg_policy`,
  (3) нулевые привилегии и ноль прочитанных строк у `anon`/`authenticated` по
  `users, classes, chat_messages, posts, files, teacher_notes`,
  (4) сам контракт: не-владелец с выданными GRANT видит 0 строк, а роль без грантов
  получает отказ до обращения к RLS. Смена роли обязана принести собственные политики.
- **Откат:** `0021` обратима повторным прогоном `0020` (политики идемпотентны:
  `DROP POLICY IF EXISTS` + `CREATE POLICY`) либо `git revert` файла миграции. Никаких
  destructive-операций в откате нет.

## 2026-10-06 (Фаза 4 — производительность)

- **Ленивая загрузка тяжёлых экранов.** Calendar (FullCalendar), Lesson (LiveKit +
  Excalidraw), Notes/Sheets/MaterialNew (Tiptap + рисование) и ClassDetail (тянет
  RichText через ленту) переведены на `React.lazy` + `<Suspense>`. Entry-чанк упал

  на сервере (в браузер не попадает). `encodings:['br','gzip']`, `threshold:0`,

  поэтому byte-range отдача файлов не затронута (проверено правами/файловыми тестами).
- **Кэш-стратегия статики (onSend в `app.ts`):** `/assets/*` (контент-хэш Vite) →
  `immutable, max-age=1y`; HTML-shell и `sw.js` → `no-cache` (revalidate по etag),
  чтобы новый деплой подхватывался сразу. Приватный API остаётся `no-store`.
- **Lighthouse/CWV не запускались** в этом окружении (нет headless Chrome Lighthouse);
  зафиксированы точные byte-size до/после и расщепление на async-чанки как измеримое
  доказательство. Полный Lighthouse-прогон — в «не проверено без реального окружения».
- **Холодный старт Render free tier** осознанно НЕ чинится (по заданию) — только отмечено.

## 2026-10-06 (Фаза 2 — согласия)

- **Единый гейт согласия вместо отдельного экрана для ролей.** `policy_acceptances`
  хранит одну строку `(userId, version, acceptedAt)`. `/api/me` отдаёт
  `policyAccepted = storedVersion === POLICY_VERSION`. SPA показывает экран
  принятия, пока это `false` — тем же механизмом покрываются и «первый вход
  учителя», и «существующие пользователи после смены версии». Регистрация ученика
  добавляет чекбокс на шаге 2 (без него submit блокируется), и после создания
  аккаунта вызывает `accept-policy`, поэтому ученик не упирается в гейт.
- **Смена версии ⇒ одно повторное принятие.** `POLICY_VERSION` (`2026-10-06`) в
  `packages/shared`. Поднять её вместе с текстами — и все примут заново при
  следующем входе. Миграций при этом не нужно.
- **Юридические тексты — черновики.** Описывают фактический стек (Render/Supabase
  Frankfurt, LiveKit Cloud для демо, Telegram, youtube-nocookie по клику). Поле
  контакта и блок несовершеннолетних — осмысленные плейсхолдеры `[…]` (НЕ пустые
  строки: тест паритета запрещает пустые значения). Правовую проверку делает владелец.
- **Тексты в локалях как массивы секций** (`privacy.sections`, `terms.sections`),
  одинаковая структура в ru/uz/en; паритетный тест рекурсивен по массивам —
  количество секций/абзацев обязано совпадать.
- **e2e-фикстуры сеют принятие** (`e2e-stack.mjs`), иначе каждая спека упиралась
  бы в гейт; спеки регистрации ставят `reg-consent`. `zz5-policy` проверяет
  и чекбокс, и пост-логин гейт на свежем аккаунте.

## 2026-10-06 (Фаза 1 — защита)

- **Callback-ключ бота отделён от JWT_SECRET (HKDF).** Подпись `callback_data`
  теперь идёт от отдельного ключа, выведенного HKDF-SHA256 из `JWT_SECRET`
  (info `klass.cb.v2`). Новые кнопки — версия `c2`; старые `c1` (HMAC по
  `JWT_SECRET`) ВЕРИФИЦИРУЮТСЯ по-прежнему, так что уже отрисованные в чате
  кнопки не ломаются — миграция подписи без переустановки кнопок. Доказательство:
  `phase1-hardening` («JWT-signed c2 refused», «legacy c1 verifies», round-trip).
- **Spike-комната LiveKit отключена в production.** Диагностический
  `/api/rtc/token` выдавал 6h publish-токен на любую `spike-*` комнату; в
  `NODE_ENV=production` возвращает 404. В dev/test/e2e остаётся рабочим
  (используется страницей `/spike` и тестом прав). TTL токена урока 6h→3h,
  spike 6h→1h, хвост имени комнаты 4→8 байт.
- **Политика пароля ≥10 + denylist частых** применяется ПРИ СОЗДАНИИ (регистрация,
  установка временного). Вход ослаблен до непустой строки — иначе аккаунты,
  созданные под старым минимумом 8, не смогли бы войти. Сервер возвращает
  переводимый код (`passwordTooShort/TooSimple/TooCommon`), сообщение на ru/uz/en.
- **`style-src 'unsafe-inline'` в CSP оставлен.** Без него Excalidraw не рендерит
  инлайн-стили холста. `script-src` остаётся `'self'` (без unsafe-inline/unsafe-eval),
  `frame-src` — только self/blob/youtube-nocookie. Принятый риск задокументирован.
- **`braces` high из `pnpm audit --prod`.** Транзитив через
  `@excalidraw/excalidraw → sass → chokidar → braces`; это BUILD-time зависимости
  (не исполняются на сервере и не попадают в раннер браузера отдельно от самой
  доски), апстрим-патча нет (`Patched <0.0.0`). Принято как документированный
  риск; CI оставлен `continue-on-error` с явным списком. `katex` low — тот же
  mermaid-поддерево.
- **Локаут перебора по аккаунту НЕ реализован** (в «Требует решения»). Пер-IP
  лимит входа 10/мин сохранён и усилен (в prod env-ослабления игнорируются).
  Полноценный email-лок конфликтует с существующим trustProxy-тестом и в
  одно-инстансной модели избыточен; предложение — таблица `login_failures`
  (см. HARDENING.md п. 1д-3).

## 2026-10-09 (язык по умолчанию — английский; признак осознанного выбора)

**Решение.** Языком по умолчанию во всём продукте становится английский: `DEFAULT_LOCALE='en'`
в `@klass/shared`, `users.locale` по умолчанию `en`, интерфейс нового посетителя — английский
независимо от `navigator.language` (его и раньше не спрашивали), `<html lang>` следует за
языком. Русский и узбекский остаются полностью доступны — перестал быть молчаливым фолбэком
только русский.

**Почему.** Симптом «выбрал en/uz, вышел, вошёл — снова русский» был не пропущенным переводом,
а порядком применения: `users.locale` для ЛЮБОЙ учётки содержал `'ru'` (дефолт колонки,
регистрация его не передавала), а `App.tsx` после входа безусловно применял язык профиля поверх
выбора устройства. Отдельно `i18n.ts` записывал в `localStorage` каждое изменение языка — включая
то, которое делал само приложение, — поэтому «выбор на этом устройстве» было невозможно
отличить от «значение применили кодом».

**Что добавлено.** `users.locale_explicit` — признак того, что язык когда-либо выбирал человек
(сайдбар, страница профиля, экраны входа/регистрации, `/language` в боте). Порядок теперь
один и он проверяется юнит-тестами: профиль, если он выбран явно > `localStorage` > `en`.
Выбор, сделанный до входа, переносится в аккаунт при регистрации и при первом входе.

**Существующие пользователи (одноразово, миграция 0024).** `UPDATE users SET locale='en'
WHERE locale_explicit = false`. Признака раньше не было, значит ни одна учётка не могла
похвастаться записанным выбором — под шаг попадают все. Это осознанный выбор задачи: значение
`'ru'` у старых строк был следствием дефолта колонки, а не решения человека. Кто реально
выбирал язык через интерфейс, у того профиль и дальше ведёт себя как выбранный: сайдбар и
страница профиля и до этого писали `locale` в `/api/me/profile`, а с 0024 любой PATCH с другим
языком ещё и выставляет флаг. Откат — `UPDATE users SET locale='ru'` (данные не удалялись),
но делать этого не нужно: язык меняется в два клика.

**Что ещё всплыло.** Тест «выйти и зайти снова» показал настоящий дефект: `logoutAll()` в
клиенте слал `fetch` без заголовка Authorization на эндпоинт под `app.authenticate` → всегда
401 → сессии не отзывались, а перезагрузка молча возвращала пользователя в приложение
(трасса: `POST /api/auth/logout-all → 401`, затем `POST /api/auth/refresh → 200`). Исправлено:
запрос идёт через общий `api()` (bearer + одинарный refresh), локальный токен сбрасывается в
любом случае.

**Серверные тексты (тот же дефолт).** Осталось два места, где русский был зашит как молчаливый
фолбэк, и оба переведены на `DEFAULT_LOCALE`: очередь уведомлений для ТЕЛЕГРАМ-ГРУППЫ
(`notify.ts`, `chat_locale` у группы нет — язык группы это отдельное решение, а не дефолт) и
`verifyAccessToken`, где отсутствующая claim `locale` читалась как `'ru'`. Личные сообщения
как и раньше идут на языке профиля. ICS локализации не содержит вовсе (в `events.ts` нет
шаблонов с текстом интерфейса), а почтового транспорта в проекте нет — ни одного файла с
SMTP/nodemailer/sendgrid/mailgun, поэтому «письма по-английски» проверить не на чём; честно
отмечено в отчёте, а не выдумано.

## 2026-10-10 (журнал миграций проигрывается одной транзакцией — что это запрещает)

**Решение.** Все значения enum-типов, на которые ссылается `DEFAULT` или данные, объявляются в
первом же файле журнала (`0000_absent_dragon_man.sql` для `app_locale` содержит `ru, uz, en`).
`ALTER TYPE ... ADD VALUE` оставляется только для случаев, когда тип расширяется в том же файле,
где его и используют.

**Почему.** CI упал на `SET DEFAULT 'en'` с SQLSTATE 55P04 («ADD VALUE is not supported before
committing the current transaction»). Мигратор drizzle на postgres-js применяет ВЕСЬ журнал в
одной транзакции, поэтому значение, добавленное в раннем файле, недоступно в позднем. Локально
это НЕвоспроизводимо: embedded-postgres здесь — 18.4, где ограничение снято, а в CI —
`postgres:16-alpine`. То есть проверка «на моей машине всё чисто» по определению не покрывает
чистую установку, которую получит владелец.

**Что добавлено.** `apps/api/test/integration/migrations-from-scratch.test.ts`: создаёт временную
БД, прогоняет журнал тем же кодом, что и сервер на старте, сверяет дефолт `locale`, состав enum
`comments_mode` и позу RLS/грантов новых таблиц, затем удаляет БД. Это единственный офлайн-прогон
пути «база с нуля», и он обязан оставаться зелёным для каждой новой миграции.

## 2026-10-10 (PATCH /api/me/profile: язык теперь необязателен в теле)

**Решение.** Поле `locale` в `profileUpdateSchema` стало опциональным. Отсутствие поля означает
«язык не трогать»; присутствие — «это выбор человека» (как и раньше, `locale_explicit` ставится
только когда значение реально отличается от лежащего в базе). Клиентские места, которые язык не
выбирают, больше его не пересылают: автосинхронизация часового пояса (`App.tsx`, `syncTz`) и экран
имени (`CompleteName.tsx`).

**Почему.** CI-прогон 37974043289 (`12a82fb`) упал на `zz15-locale.spec.ts:148`: выбран uz на экране
входа, после входа интерфейс стал английским. Это не флейк: сразу после входа SPA шлёт ДВА PATCH'а
профиля — перенос выбора языка (`locale: 'uz'`) и синхронизацию TZ (`tz: 'UTC'`, и в неё раньше
попадал `locale` из снапшота профиля, то есть `'en'`). Порядок их завершения не гарантирован. Если
последним прилетает TZ-синхрон, сервер видит «locale изменился с `uz` на `en`» и ставит
`locale_explicit = true`: автоматическая синхронизация выдаётся за осознанный выбор, а следующий
`refresh()` обязан подчиниться профилю — интерфейс английский. Локально баг не воспроизводится ПО
ПРИЧИНЕ: машинка разработчика живёт в `Asia/Tashkent` — ровно такой TZ лежит во всех фикстурах,
поэтому `syncTz` выходит по раннему `return` и никогда не стреляет; раннер GitHub — в UTC, там он
стреляет всегда. Проверяемо: новый e2e-тест с `timezoneId: 'UTC'` и задержкой TZ-запроса даёт
детерминированное `{"visible":"en","syncs":1}` до правки и `{"visible":"uz","syncs":1}` после.

**Что это меняет для других вызовов.** Ничего: `Nav.pick`, страница профиля, регистрация и все
скрипты по-прежнему присылают `locale`, то есть по-прежнему выбирают язык явно. Валидация не
ослаблена — неизвестное значение (`'de'`) и отсутствующее `name` остаются 400, это закреплено
тестом. Права, лимиты и RLS не тронуты: новых грантов нет, `locale_explicit` по-прежнему ставит
только сервер.

экран, который учитель уже разрешил, остаётся; обратно — базовая линия урока
(`studentPermission(lectureMode, hadScreen)`). Ни токен на вход, ни чьи-либо ещё права не
расширяются. Микрофон в браузере ученика включает САМ ученик: сервер это сделать не может.

**Почему именно так (измерено, а не предположено).**
* `MutePublishedTrack(muted: false)` LiveKit отвечает `412 remote unmute not enabled` (лог CI
  2026-10-10, спек `zz-camera`). Значит «включить микрофон ученику удалённо» физически недоступно
  без смены политики сервера, и вариант «сервер сам unmute'ит» пришлось бы покупать правом, которого
  у нас нет.
* `RoomServiceClient.d.ts`: права обновляются атомарно — «all desired permissions would need to be
  set». Запись `{ canPublish: true, canPublishSources: [MICROPHONE] }` молча отобрала бы
  разрешённый ранее показ экрана. Поэтому грант композится, а не перезаписывается, и это
  закреплено юнит-тестом (`apps/api/test/unit/floor-permission.test.ts`).
* Направление «заглушить» работает, поэтому отзыв слова делает две вещи: возвращает базовую линию
  И глушит уже опубликованный аудиотрек (`mutePublishedTrack(..., true)`). Иначе ученик продолжал
  бы вещать после того, как слово забрали.

**Риск, который остаётся, и почему он принят.** Грант без удалённого unmute означает, что между
«учитель дал слово» и «ученика слышно» стоит браузер ученика. Он не откроет микрофон, если вкладка
закрыта, если человек не дал разрешения устройству, или если приложение на его стороне глупее
сокет-кадра. Это не дыра в правах, а свойство выбранной схемы: сервер не может обещать «слышно»,
поэтому он и не обещает — `grant` отвечает 502 и НЕ пишет `granted_at`, если LiveKit недоступен
(тест «giving the floor without a reachable media server records nothing»), а отзыв, наоборот,
сначала убирает факт, потом пишет разрешение, чтобы отказ медиа-сервера не мог оставить ученика
без возможности его заткнуть. За «ученик нажал кнопку у себя» отвечает клиент: `acceptFloor()`
показывает ошибку микрофона, а не проглатывает её.

**Чего это стоит в правах.** Ничего нового: ни `roomAdmin`, ни `canUnmute`, ни widened token.
Единственный чувствительный участок — `canPublishSources` этого одного человека на время, пока он
держит слово; он сворачивается при отзыве, при том что ученик сам опустил руку, и при `lower-all`.
Урок, законченный через `/end`, чистит очередь (`clearHands`) и кикает участников, то есть
разрешение вместе с сессией.

## 2026-10-10 (access-лог: ключ `req`, маска сегмента пути и тест на выводе)

**Решение.** Сериализатор доступа живёт под именем `accessLogOptions` (тот же файл `src/app.ts`) и
подключается ключом `serializers.req`. `buildApp(db, { logger })` принимает готовый логгер, чтобы
тест мог собрать реальное приложение с РЕАЛЬНЫМИ опциями. `sanitizeRequestUrl` кроме query
маскирует и сегмент пути `/api/ical/<token>`.

**Почему это отдельная запись.** Три месяца зелёного CI соседствовали с тем, что в access-лог
попадали одноразовые WS-тикеты, а в `/api/ical/…` — персональный ICS-токен. Причина не в функции
(она была правильная и покрытая тестом), а в имени ключа: pino читает `serializers.req/res/err`,
`request` молча игнорируется, TypeScript не возражает. Отсюда правило для этого репозитория:
**настройки, которые влияют на текст наружу (логи, заголовки, коды ответов), проверяются по
выводу, а не по аргументам функции.** Юнит-тест `sanitizeRequestUrl` теперь не одинок: рядом
`test/integration/access-log.test.ts`, который читает строки, написанные логгером.

**Что сознательно оставлено.** `logger.redact` по заголовкам — пути никогда не совпадали (ни
дефолтный, ни наш сериализатор заголовки не отдают), оставлено как второй слой. И открытый
вопрос: может ли сообщение ошибки postgres-js включать строку подключения — не проверялось,
потому что проверка требует подставить значение, похожее на секрет.

## 2026-10-10 (текст ошибки печатается без message; конфигурационный отказ — без значений)

**Решение.** Любая печать исключения наружу (boot-`console.error`, `console.warn` в обвязке
Telegram, `req.log.warn` вебхука, `serializers.err` у access-лога) идёт через
`apps/api/src/lib/redact.ts`: либо `describeError` (класс + коды, без message вовсе), либо
`safeErrorMessage` (message до маркера `params:`, пропущенный через redactor паттернов).
`envSchema.parse` → `safeParse` и печать имён ключей.

**Почему, а не «на всякий случай».** Измерено на фиктивных значениях: ошибка `postgres-js`
несёт строку подключения в `message` (`code: ENOTFOUND`, `syscall: getaddrinfo`), а обёртка
drizzle — `Failed query: <SQL>\nparams: <значения>`; в этом проекте в значениях бывают почты и
тексты чата. `ZodError` при отказе конфигурации кладёт принятое значение в `received`, то есть
`JWT_SECRET` попал бы в вывод Node до всякого логгера. Прежний ручной
`replaceAll(env.TELEGRAM_BOT_TOKEN, '***')` закрывал один токен из одного места.

**Что это стоит.** Строка `boot failed: DrizzleQueryError (ENOTFOUND, -3008)` менее
человекочитаема, чем полный message — это сознательный обмен: код и класс достаточны, а цена
утечки в этой системе (чужие уроки и переписка) выше удобства.

**Проверка.** `test/unit/redact.test.ts` (17) и `test/integration/boot-error-output.test.ts` (3,
реальный процесс `dist/server.js` с фиктивным `DATABASE_URL`); обе проверяют вывод, а не функции.

## 2026-10-11 (часть 2 урока: не менять то, что замер не показал; счётчик без опроса)

**Решение.** Из правок, перечисленных в задаче, сделаны только те, что опираются на число:
разделение чанков (lazy `/spike`, lazy доска/панель/комментарии), выключение пробы «где идёт
урок» на `/lesson*`, статус урока раз в 30 с внутри комнаты, страховка очереди рук раз в минуту,

тайлов, остальные на паузе» и автоматическое снижение качества при слабом канале.

**Почему.** Замер (учитель + 3 ученика, 4 тайла с настоящими кадрами, 30 с покоя): 0 длинных

(0.282 и 0.388 с) больше, чем разница между сборками. Спрятать часть участников — изменение
поведения, которое нельзя отменить одним флагом, и оно не куплено ни одной измеренной миллисекундой.
Пауза входящего видео в проекте уже есть (кнопка в «Ещё» + `adaptiveStream: true`), и она
срабатывает там, где проблема настоящая — на канале, а не на CPU клиента.

**Счётчик непрочитанных — отдельные сутки.** Прежний фоновый опрос `/comments` раз в 20 с был не
только трафиком: `GET` отмечает прочтение на сервере, поэтому опрос сам обнулял счётчик, и человек
мог не увидеть ни одного «непрочитанного». Теперь это один сид-запрос при входе плюс кадры
`comment` из уже открытого сокета, с нулём при открытой вкладке. Проверка zz16 сравнивает
конкретное значение до и после чужого сообщения, zz18 следит, что за 30 с с закрытой панелью к
`/comments` не обращаются ни разу.

**Что это стоит.** Счётчик живёт на сокете: если сокет оборвался, а человек остался на странице,
новое сообщение он увидит не сразу (прежний опрос догонял за 20 с). Принято сознательно: фоновый
опрос платил за эту страховку обнулением того, что показывал.

**Что не измерено и не обещано.** Потолок 720p проверен только кодом: фейковая камера отдаёт
640×480 независимо от запроса, так что «стало легче на слабом канале» без реальной камеры не
доказано. Холодный старт Render (32.8–33.0 с) и ход до LiveKit Cloud (2.5–2.8 с до первого кадра)
правкой кода не меняются.

## 2026-10-13 — часть 1: после режима лекции устройства возвращает клиент, а сервер отвечает 502

**Решение.** Выключение режима лекции больше не может называться успехом, если медиа-сервер не
ответил: маршрут сначала читает ФАКТИЧЕСКОЕ разрешение каждого ученика и возвращает базовое,
сложенное с ним, и только потом пишет `lectureMode = false`. Недоступный сервер — 502 и прежнее
состояние в базе. Решение учителя «вернуть микрофоны и камеры после лекции» хранится колонкой на
сессии (`lesson_sessions.lecture_restore`) и приходит вместе со статусом, а не живёт в компоненте.

**Почему так, а не «просто включить всем микрофоны».** LiveKit не умеет удалённо включать трек:
`MutePublishedTrack` с `muted: false` отвечает 412 (замерено 2026-10-10, записано в
`services/lessons.ts`). Значит сервер обязан вернуть только ПРАВО, а устройство включает сам
ученик по кадру `lecture_off`. Прежний порядок (записать состояние, потом молча попытаться
выдать права через `media()`, который глотает ошибку) и порождал симптом: 200, «режим выключен»,
и класс, который физически не может заговорить до конца урока.

**Что это стоит.** Учитель при недоступном LiveKit получает 502 и должен нажать кнопку ещё раз —
повтор идемпотентен, потому что разрешение вычисляется, а не прибавляется. Ученик, который
перезагрузил страницу посреди лекции, попадает в тот же разряд, что и пришедший во время неё:
снимок «что было включено» снимается в момент включения лекции, и восстановить его после
перезагрузки негде — такой ученик включает себя сам одним нажатием. Отдельно и честно: показ
экрана, выданный ДО лекции, после выключения не возвращается само по себе — при включении лекции
список `canPublishSources` обязан стать пустым, потому что он важнее `canPublish` (это описано и
проверено в `floor-permission.test.ts`), так что «помнить» выданный показ было бы негде, кроме
новой таблицы; этого в задаче не было, и мы её не заводили.

**Изменённые существующие тесты.** `lesson-comments.test.ts` («комментарии при лекции»): ожидание
`200` для выключения лекции заменено на `502` плюс «состояние не изменилось» — утверждение стало
строже, предмет теста не тронут. `zz2-moderation` и `zz18-control-bar`: включение лекции теперь
требует подтверждения, в них добавлен обязательный клик по «Включить»; все прежние проверки
остались.

**Проверка.** Юнит: арифметика возврата (`floor-permission.test.ts`, +2 случая). Интеграция:
`lecture-restore.test.ts` — переключатель на сессии и в статусе, 502 без изменения состояния,
400 на не-переключатель, 403 ученику и одинаковый 404 на чужой/несуществующий урок. Браузер:
`zz19-lecture-restore.spec.ts` — трое учеников (горевшее возвращается, выключивший себя до лекции
молчит, пришедший во время лекции молчит), кнопка «Выключить» в тосте, вариант «не возвращать».

### 2026-10-13 — диагностика zz19: порядок прихода событий, а не «таймер подождать дольше»

**Что молчало.** Первый же браузерный прогон падал в CI и проходил локально: `Анна` не получала
обратно микрофон, который горел до лекции (`aria-pressed` оставался `false`).

**Как это было измерено, а не угадано.** В Playwright добавлены `trace: 'retain-on-failure'` и
скриншоты падения, а job `e2e` — выгрузку `test-results` артефактом на 7 дней. Локально запущен
тот же сценарий с живой комнатой, а порядок CI воспроизведён детерминированно: кадры ученика
задержаны через `page.routeWebSocket`, поэтому сигнал комнаты приходит раньше нашего кадра.
Замеренные таймстемпы (мс от загрузки страницы):

```
кадр lectureMode on=true      у ученика НЕ было      (в CI-порядке кадр опаздывает)
perms canPublish=false        11305   ← комната отняла право
LocalTrackUnpublished mic     11323   ← и сняла опубликованные треки
LocalTrackUnpublished cam     11350
frame lectureMode on=true     19306   ← наш кадр пришёл ПОСЛЕ всего
snapshot mic=false cam=false          ← снимок, сделанный по кадру, пустой
```

**Причина.** Маршрут `/lecture-mode` сначала отдаёт команды RoomService (`updateParticipant`), а
`wsBroadcast` шлёт после. Когда комната и API живут на 127.0.0.1 (CI: контейнер
`livekit/livekit-server:v1.13.9`), браузер узнаёт об отзыве публикации раньше, чем о начале
лекции, — и снимок «что горело», который делался по кадру `lectureMode`, показывал `false/false`.
Возвращать было нечего, поэтому микрофон ученика не включался НИ ОДНАжды: никакие повторы тут не
помогали (предыдущая правка с таймером на 4 попытки это не лечила — проверено тем же прогоном).

**Что отвергнуто фактами.** (б) «права приходят позже кадра, и таймер не успевает» — нет: права
как раз приходили РАНЬШЕ кадра (`perms canPublish=true` в 15429 против кадра в 24103). (в) «в
наборе источников нет микрофона или камеры» — нет: возвращённый набор `src=[1|2]`, то есть
CAMERA+MICROPHONE. (г) «разница версий LiveKit» — локально проверить нельзя: Docker на этой машине
отсутствует, поэтому контейнер v1.13.9 тут не запускается, а облачный узел версии не сообщает
(`room.serverVersion` в этом соединении не заполнен). Разница CI/локально объясняется задержками, а
не версией: локально кадр успевал первым, в CI — нет.

**Как исправлено (итог, после второй итерации).** Снимок «что горело до лекции» перенесён на СЕРВЕР.
Маршрут включения лекции читает `listParticipants` ДО цикла отзыва публикации и пишет карту
`identity → {mic, cam}` на сеанс (миграция 0028, колонка `lecture_pre_devices`). Сервер делает
снимок в тот момент, который сам же и меняет, поэтому порядок «что дошло до браузера раньше — сигнал
комнаты или кадр `lectureMode`» на него не влияет, и снимок переживает перезагрузку страницы ученика
посреди лекции. Первая правка (2026-10-13 утро) пыталась снять это на клиенте при каждом изменении
локальных треков — от этого отказались: это чинило лишь один из двух порядков и теряло состояние
при перезагрузке.

**Приватность и время жизни снимка.** Из карты наружу отдаётся только запись спрашивающего
(`session.preLecture`); полная карта (`session.preLectureRoster`) — владельцу урока, учителю. Чужой
класс и несуществующий отвечают одинаковым 404. Снимок живёт ровно столько, сколько лекция:
выключение лекции и завершение урока стирают его (`setLecture(false)` и `endLesson` пишут `{}`).
Отсюда следует вторая половина дизайна: клиент обязан ЗАПОМНИТЬ свою запись, пока лекция идёт, —
запрос статуса после `lecture_off` вернёт уже пустоту. Идёт за ней ученик по СОБЫТИЮ КОМНАТЫ (право
публиковать отозвано: `noteLectureStartedByRoom` → `rememberMySnapshot()`), а не по нашему кадру
`lectureMode on`: кадр может дойти уже после выключения, когда сервер стёр карту. Вход и
переподключение приносят снимок в кадре `started` и в опросе статуса; при выключении возврат берёт
remembered значение, а не идёт на сервер за ним.

**Что на клиенте осталось.** Устройство включает сам ученик (LiveKit отвечает 412 на удалённое
включение). Включение событийное: `setMicrophoneEnabled` пробуется сразу, а при 403 «insufficient
permissions» `waitCanPublish` ждёт СОБЫТИЯ `ParticipantPermissionsChanged` с `canPublish=true` и
нужным источником — не дольше `RIGHTS_WAIT_MS` (5 с). Порог — страховка от потерянного события, а не
подстройка под медленную машину: таймера-опроса по состоянию (в первой правке был цикл раз в 250 мс
и ожидание 20 с) здесь нет намеренно, а реальную задержку распространения меряет сам спек zz19 и
печатает в CI (см. ниже «как измерено»). По таймауту показывает `lesson.lectureRestoreNoRights`
вместо тишины (три языка), а отказ устройства — свою подсказку, а не молчание. Эпизод лекции
открывается любым сигналом и закрывается ровно один раз (кадр `lecture_off` главный, переход
статуса — страховка), решение учителя держится в `lectureRestoreChoiceRef`, «выключить всех» — в
`muteAllRef`.

**LiveKit в CI и чего это стоит.** В CI RTC-спеки говорят с КОНТЕЙНЕРОМ
`livekit/livekit-server:v1.13.9` как с service-контейнером job, на тестовых ключах `e2ekey` —
секреты репозитория там не участвуют, облачный лимит CI не расходует. Локально контейнера нет
(Docker на этой машине отсутствует), и обвязка берёт `LIVEKIT_*` из `.env`, то есть из облачного
проекта: каждый локальный RTC-прогон — это реальные участники облачного LiveKit. Поэтому локальные
серии ограничены (не больше трёх прогонов подряд), а спек в `afterAll` завершает урок
(`POST /api/lessons/:id/end`), чтобы комната освободилась, а не висела до таймаута.

**Как измерялась задержка (замер снят).** zz19 ставил метки общими часами процесса теста: момент
клика учителя, момент ответа POST `/lecture-mode` (рассылка кадра происходит внутри того же
обработчика, до ответа) и момент, когда кадр пришёл в браузер ученика; плюс `lecture_off → микрофон
снова горит`. Рабочий код не правил ничего. Итоговые числа зелёного прогона 38431125402 (контейнер
LiveKit, GitHub-раннер): кадр `lectureMode on` — 409 и 358 мс от клика, из них 425 мс «клик+сервер»
и −16/−67 мс «кадр обогнал ответ»; `lecture_off` — 250 и 247 мс; микрофон снова горит через 496 мс
после клика учителя. В третьем спеке (кадры ученика держатся 8 с) метка снимается до задержки и
показывает 131–184 мс на путь API → браузер. То есть ни одна задержка кадра урока в CI не выходит
за полсекунды; «десятки секунд» были локальной машиной, а «5,7 с на кадр включения» — ошибкой самого
замера (см. ниже). Аннотации `lrm-measure`, перехват ради меток и шаг CI «Замер задержек кадров»
убраны вместе; ретранслятор кадров остался только там, где он нужен тесту — в третьем спеке.

**Что измерено в CI.** Путь «выключили лекцию → права вернулись → устройство включилось» укладывается
в полсекунды (числа и метод — в абзаце «как измерялась задержка» ниже, там же и итоговый зелёный
прогон). Значит «десятки секунд» были артефактом локальной машины, и серверный дизайн остаётся без
обходов под неё.

**Число «5,7 с на кадр включения» было ошибкой замера, и это записано, чтобы не повторить.** Первая
версия меток писала приход `lectureMode` в одну ячейку, не глядя на флаг `on`. Маршрут выключения
шлёт `lectureMode on:false` прямо перед `lecture_off`, поэтому метка «включения» перезаписывалась
моментом выключения, и дельта оказывалась интервалом между двумя кликами учителя (4953 и 5710 мс —
это расстояние от включения до выключения в первом спеке, а не задержка сокета). Метки разбиты на
три: `lectureMode_on`, `lectureMode_off`, `lecture_off`, и первая запись больше не перезаписывается.
После правки ни одной неподтверждённой задержки у кадров нет.

**Дефект, найденный красным CI-прогоном (тот же прогон, третий спек zz19).** Красным он был не из-за
порядка событий: маршрут выключения лекции обошёл список участников, у одного из них соединение
комнаты оборвалось ровно в этот момент (в логе LiveKit — `PEER_CONNECTION_DISCONNECTED`, затем
`UpdateParticipant` → 404 `participant does not exist`), вызов попал в `failed`, и учитель получил
502 с `lectureMode: true` — лекция НЕ выключилась из-за человека, который уже вышел и которому
возвращать было нечего. Правка: `isParticipantGone` (404 по участнику = «его нет», цикл идёт дальше),
а настоящий отказ медиа-сервера (таймаут, 5xx, нет соединения — кода 404 там нет) по-прежнему даёт
502 без записи состояния. Граница закреплена в `test/unit/participant-gone.test.ts`, контракт 502 —
в интеграционном тесте; в CI это всплыло в третьем спеке zz19, где страницы предыдущих спеков ещё
не вышли из комнаты, а новый вход уже идёт (в логе LiveKit — `DUPLICATE_IDENTITY` рядом).

**Второй дефект того же спека (прогон 38426209204): клиент помнил снимок только со времени кадра.**
Ученик шёл за своей записью на кадр `lectureMode on`. Сокет ученика в третьем спеке задержан на 8 с,
лекция за это время успевает кончиться, сервер снимок стирает — и на `lecture_off` в кэше пусто,
устройство не включается молча. Правка: снимок берётся ПО СОБЫТИЮ КОМНАТЫ (отзыв права публиковать),
которое делает те же самые руки, что перед этим записали снимок, поэтому оно не может опоздать за
пределы лекции; опоздавший кадр больше не затирает запомненное пустым ответом.

**Попутно найденный дефект панели.** Меню «Ещё» остаётся открытым после пунктами-переключателей
(режим лекции), а тестовый помощник `openMore` кликал по кнопке всегда — второй вызов закрывал
открытое меню, и следующий клик падал на исчезнувшем элементе. Помощник стал идемпотентным, как
`openTab` (это навигация в тесте, не ослабление проверки).

**Ещё одно следствие порядка.** Отзыв публикации LiveKit делает не «mute», а снятие трека
(`LocalTrackUnpublished`) — утверждение в шапке zz19 («LiveKit не останавливает уже опубликованный
трек») было неверным для этого пути; оно исправлено в комментарии спека.


## 2026-10-14 — ночь: часть 3, доска для учеников с разрешения учителя

**Почему право и авторство живут на сервере, а не в клиенте.** Комната доски (`routes/board.ts`)
принимает сообщения от имени того, кто открыл сокет, и любой запрет на клиенте обходится одним
`ws.send()`. Поэтому: `board_draw_all` / `board_draw_students` лежат на сессии (миграция 0029),
проверяются на КАЖДОМ сообщении, а не при подключении, и автор элемента — это `userId` сокета,
записанный сервером в `whiteboards.authors`. Поле `authorId` в присланном элементе сервером не
читается вообще: тест «поддельный автор» на этом и построен.

**Отзыв действует сразу — проверкой до merge.** Обработчик сначала сверяет право и только потом
пишет в сцену, поэтому из опоздавшего или запрещённого кадра в доске не оказывается ни одного
элемента (а не «появился и откатился»). Чужой элемент дополнительно возвращает отправителю
авторитетный снимок страницы: версии у его локальной копии уже выше, чем у отброшенного элемента,
и точечная доставка ничего бы не исправила.

**Учитель не крадёт авторство.** Поправив ученический штрих, учитель не становится его автором —
иначе «удалить рисунки ученика» оставляло бы на доске ровно то, что ученик и нарисовал, и действие
теряло бы смысл.

**`locked` — удобство, а не защита.** Excalidraw 0.18.1 не поддерживает проп `lockedElements`
(в этом билде его нет), но уважает свойство элемента `locked`: такой элемент нельзя выделить
кликом, лассо, «выделить всё», сдвинуть, изменить размер и стереть ластиком. Поэтому сервер
навешивает `locked` на чужие элементы ПЕРСОНАЛЬНО при рассылке ученику, а из входящего кадра это
поле выкидывает — иначе ученик мог бы «разблокировать» чужой рисунок. Право при этом по-прежнему
решает `gateEdits`.

**Лимиты считаются накопленно.** Кадр несёт до десятков элементов, поэтому 300 элементов и 1 МБ
на ученика на доску проверяются по мере принятия элементов одного кадра, а не по каждому отдельно
(иначе один кадр проносил бы столько, сколько в него влезло).

**Размер кадра проверять в обработчике бессмысленно.** Потолок стоит на сокете
(`maxPayload: 256 КБ` в `app.ts`), и сообщение больше него до логики доски не доходит — соединение
обрывается на уровне протокола (в тесте это 1006/1009). Первая версия проверки на 2 МБ была бы
мёртвым кодом, и ключ локализации «кадр слишком большой» убран вместе с ней.

**GET `/board` отдаёт сохранённый снимок, а не живую комнату.** Комната доски живёт в памяти и
сбрасывается в базу раз в 10 с, поэтому интеграционный тест читает состояние из `init` нового сокета
(это и есть живая сцена), а к REST обращается только там, где важна именно запись в базу.

## 2026-10-14 — часть 4: архив завершённых уроков

**Архив — это вид, а не копия.** Отдельной «архивной таблицы» нет: список собирается из
`lesson_sessions` (дата и длительность), `whiteboards` (сцены), `lesson_comments` (расшифровка) и
`lesson_attendance` (приход/уход). Копия была бы вторым источником правды, который всегда отстаёт
от первого, и её пришлось бы чинать при каждом удалении доски.

**Выключенный архив неотличим от чужого класса.** Ученику без переключателя класса ответ — тот же
404 с тем же телом, что и запросам в чужой класс и к выдуманному id (проверяется сравнением тел в
`lesson-archive.test.ts`). 403 здесь означал бы «такой класс существует», и это утечка.

**Ученику положены только доски.** Число комментариев, список комментариев и список присутствовавших
сервер не отдаёт при `boardArchivePublic = true` никак — не «скрывает на клиенте». Включение
переключателя по умолчанию выключено, поэтому по умолчанию ученик не видит ни-чего.

**Присутствие — персональные данные, и это отдельная таблица.** `lesson_attendance` хранит
`(урок, человек, пришёл, ушёл)`: первая строка на пару `onConflictDoNothing` (переподключения не
множат записей), уход пишет сокет-`close` и завершение урока. Больше здесь ничего нет: ни «кто
сколько молчал», ни микрофон. Раз таблица новая — поза доказана на чистой базе в
`migrations-from-scratch.test.ts` (RLS включён, политик нет, ни одной выдачи не-владельцу, права
колонок через `has_column_privilege`).

**Раз формулировка политики изменилась — версия тоже.** Добавились новые данные (время прихода и
ухода с привязкой к человеку), поэтому текст политики обновлён на трёх языках и `POLICY_VERSION`
поднят с `2026-10-06` на `2026-10-14`. Побочный эффект, о котором надо знать: каждый существующий
пользователь при следующем входе один раз увидит экран согласия. Откат — одна строка в
`packages/shared/src/constants.ts` плюс две строки `version` в локалях.

**Срок хранения по умолчанию ничего не удаляет.** `BOARD_ARCHIVE_RETENTION_DAYS = 0` ⇒ уборщик не
вызывается вовсе; при положительном значении удаляются только ЗАВЕРШЁННЫЕ уроки старше срока, и
дело это делает каскад в базе (доски, комментарии, руки, присутствие уходят вместе с записью).
Идущий урок старше срока — не архив, и его уборщик не трогает (это отдельная проверка теста).

**`${column}` внутри `sql` в списке SELECT — ловушка.** Дренч разворачивает его голым `"id"`, и в
корреляционном подзапросе такое имя относится к таблице подзапроса:
`(select count(*) from lesson_comments c where c.lesson_session_id = "id")` считало `c.id`, то есть
ноль. Молчаливая ошибка: `boards` при 1 и `comments` при 0 на одной строке. Теперь таблица в
подзапросе названа явно (`"lesson_sessions"."id"`), и это стоит в комментарии прямо над запросом.

**Прямое сохранение страницы ограничивает транспорт, а не код маршрута.** Глобальный потолок тела
Fastify — 1 МБ, потолок сцены — 2 МБ, значит на `PUT /board/page` проверка «2 МБ» недостижима:
запрос отсекается раньше, и `config: { bodyLimit }` в этом билде ничего не поднимает (он не проходит
типизацию маршрута и не действует). Мёртвая проверка убрана; тест теперь честно ждёт 413 и
«ничего не записано». Потолок сцены при этом остаётся живым там, где он реально срабатывает: в
живом мердже доски, где кадры по 256 КБ накапливаются в сцену больше 2 МБ.

## 2026-10-14 — часть 5: экспорт доски в Word

**Миграция 0030 учила не коду, а порядку применения.** `REVOKE ... FROM anon` на обычном Postgres —
ошибка 42704 («role does not exist»): роли `anon`/`authenticated` создаёт Supabase. Локально баг
невидим, потому что кластер `.pgdata` эти роли уже имеет, и CI это поймал первым (`38498739402`:
красными стали ВСЕ интеграционные наборы и smoke — сорвался `migrate()`). Правка — поза из 0025:
DO-блок с проверкой `pg_roles`. Доказательство с обеих сторон: чистый кластер без ролей (весь журнал
с 0000) и локальный прогон `migrations-from-scratch` с ролями.

**Word и PDF рисуют один и тот же кадр.** Картинки собираются одним циклом (`exportToBlob`,
`document.fonts.ready`, масштаб 2, белый фон) и только упаковка разная. Два пути растеризации
означали бы, что «то, что увидел родитель в PDF» и «то, что открыл учитель в Word» могут
разойтись, а проверить это дешевле одного раза.

**Размер страницы у Word не выбирается.** Выбор «A4 / по содержимому» — про PDF; документ Word по
постановке всегда альбомный A4 с полем 10 мм, поэтому у кнопки Word нет своего селектора, и
существующий селектор относится только к PDF (в подсказке окна это сказано).

**Библиотека остаётся ленивой, и это измерено.** `docx` 9.11.0 (MIT по установленному пакету)
подгружается по нажатию: отдельный чанк 408,25 КБ (119,69 КБ gzip). Начальный чанк вырос на 2,3 КБ —
это подписи трёх языков, а не библиотека. `pnpm audit` относит обе найденные уязвимости к
`@excalidraw` (mermaid→katex, sass→braces); `docx` не добавляет ни одной.

**Имя файла чистит одна функция.** PDF и Word обязаны называться одинаково (класс может содержать
кириллицу и `oʻ/gʻ`), поэтому `boardPdfFileName` и `boardWordFileName` оба идут через
`boardExportBaseName` — иначе правила именования разъезжаются при первой же правке одной из кнопок.

**Переключатель класса НЕ отключает доступ к доске того урока, на котором ученик был.** Первая
версия части 4 навешала условие «архив» и на `GET /api/lessons/:id/board` (завершённый урок ⇒
ученику 404, пока учитель не включил переключатель). CI это поймал существующим тестом прав
(`rights.test.ts`, ожидание 200): маршрут с самого начала обслуживал « reopening after the lesson»
(§3.7), и молча отнять у всех учеников уже работающий доступ — это не часть постановки, а скрытая
регрессия, тем более что переключатель по умолчанию выключен. Условие с маршрута снято; раздел
«Архив уроков» (где есть список, навигация и расшифровка) остаётся под переключателем полностью.

## 2026-10-15 — RTC-спека: вход в комнату и `page.goto` не смешивать

**Симптом, который три прогона выглядел как продуктовый баг.** `zz20-board-students`, проверка
«учитель даёт право рисовать Анне»: `getByTestId('peer-draw-8d7d9d9c')` не найден за 30 с. Ряд
участника безусловно рендерится в `LessonPanel.tsx`, поэтому казалось, что панель не видит ученика.

**Разбор трассы (`gh run download 38541787520` → `trace.zip`, по контекстам) закрыл вопрос фактами:**
учитель подключился (755673) и отключился (765544) ровно на `Frame.goto /lesson?classId=…` — это
`openLesson`, который спек вызывал ПОСЛЕ `join`; то же у обоих учеников (769101, 771746). LiveKit SDK
сам вешает `beforeunload`-обработчик и пишет в консоль `Page leave detected, disconnecting` →
`disconnect from room`. Переподключения нет: после перезагрузки в урок входят кнопками предпросмотра
устройств, а тест их больше не трогал. На момент проверки (774186) в комнате не было никого, и
панель показала «Участники · 0 / Пока нет учеников» — ARIA-снимок падения это и фиксирует.

**Решение: правка спеки, продукт не тронут.** `Lesson.tsx:refreshPeerList` строит список из
`room.remoteParticipants`, поэтому пустая панель при несоединённой комнате — корректное поведение, а
не ошибка. Разделённые состояния «до входа» и «в комнате» тест должен создавать сам: для доски есть
`openLesson` (переход + ожидание полотна), для комнаты — `join` без всякого перехода после. Новый
`waitBoard(page)` ждёт ровно те же состояния, что `openLesson`, но без `goto` и без `waitForTimeout
(1500)`. Проверки не ослаблены: к ним добавлено ожидание «в панели ровно 2 ряда участников» — оно и
называет причину яснее, чем отсутствующий локатор.

**Правило на будущее (стоит помнить по всем zz2/zz17/zz18/zz19/zz20):** после входа в комнату
навигация запрещена; нужен переход — сначала переход, потом вход. Доска вне звонка тоже существует
(карточка под сеткой, часть 4), поэтому «переход разорвал комнату» не виден по зелёному ожиданию
`board` — red-тест ловит только следующая за ним проверка, и по её тексту причина не читается.

## 2026-10-16 — контролируемый редактор: обратная запись только по смене документа

**Симптом.** Красный zz10 в прогоне `38739607672`: вместо `Проверка редактора жирный` получилось
`Проверка редактораирныйж` — первый символ, напечатанный после кнопки «жирный», встал ПОСЛЕДНИМ.
Трасса прогона снимков DOM не содержит (в `playwright.config.ts` был `trace: 'retain-on-failure'`
без `snapshots`), поэтому промежуточные состояния редактора восстановить было нечем — это
отдельная причина, по которой снимки включены (см. ниже).

**Что измерено, а не предположено.** Первой гипотезой было «родитель возвращает эхо позже, чем
документ ушёл вперёд, и обратный `setContent` откатывает документ назад». Гипотезу проверяли
приборкой прямо в собранном `RichText`: счётчик срабатываний условия «`value` короче текущему
документу» за 9 прогонов не вырос ни разу. Тогда гонку сделали принудительно (новый zz24): React
планирует пассивные эффекты доставкой `MessagePort.postMessage`, сценарий задерживает каждую
доставку на 60 мс, печать — 1 мс на символ, 55 символов, два переключения формата, плюс прогон с
`Emulation.setCPUThrottlingRate` 4×. Итог: в форме материала символы не теряются ни до, ни после
правки. Причина — семантика React: один рендер забирает ПОСЛЕДНЕЕ поставленное состояние, поэтому
эхо родителя не может быть старше документа. Гипотеза опровергнута, а не «не повезло поймать».

**Что нашлось вместо неё — реальная потеря данных.** Тот же принудительный тест на заметках
красный: автосейв заметок (`queueSave`, 800 мс) берёт идентификатор заметки в момент срабатывания
таймера, а не в момент набора. Если учитель напечатал и сразу открыл другую заметку, текст первой
уходит ВО ВТОРУЮ. В прежнем коде это и произошло: в заметку B легло «Гонка A … альфа bravo 0123456789
чарли delta …». Это ровно та потеря, ради которой проверка и писалась.

**Решение.**
1. Общий хук `apps/web/src/lib/controlledEditor.ts` для обоих редакторов (форма материала, лента,
   заметки): значение из props пишется в документ только когда сменился `docId` (другая заметка или
   материал, первая инициализация) либо когда редактор не в фокусе и значение правда отличается и
   не является эхом собственной отдачи. Пока в редакторе печатают — обратная запись запрещена.
2. Отдача родителю накоплена дебаунсом (200 мс), но с гарантиями: немедленный flush по blur (клик
   по «Опубликовать» или по другой заметке уводит фокус ДО обработчика клика), при размонтировании,
   при смене документа и по требованию страницы через `handle.flush()`. Если документ отстал от
   того, что редактор уже набрал (замена экземпляра после уничтожения — окно, ради которого написан
   zz10), документ догоняется СВОИМ значением, а не значением родителя.
3. Заметки: у накопленного патча есть владелец (`pendingOwner`), смена заметки сначала отдаёт
   последние символы (`rtRef.flush()`), затем сохраняет их (`saveNow()`), и только потом
   переключается. Продвижение черновика в реальную заметку передаёт владельца новому id.
4. Панель заметок получила доступные имена и testid (`rt-bold`, `rt-italic`, `rt-h2`, `rt-ul`,
   `rt-ol`, `rt-undo`, `rt-redo`): кнопки «B», «•», «1.» экранному диктору ничего не говорили, а
   тесту — не на было опереться. Новый ключ `material.heading` добавлен сразу в ru/uz/en.
5. `apps/e2e/playwright.config.ts`: трасса красных тестов теперь ведётся со `{ snapshots: true,
   sources: true }`. Красный случай в редакторе без снимков DOM неразбираем — этот прогон это
   показал.

**Останется зафиксированным как не объяснённое.** Единичная перестановка символа в zz10 в CI не
воспроизведена ни в одном из локальных сценариев (обычная печать, форсированное эхо 60 мс, CPU×4,
60 символов с форматами). Правка убирает класс причин (обратную запись в печатающий документ) и
добавляет тест, который этот класс ловит, но утверждать, что именно она чинит тот прогон, нельзя.

## 2026-10-16 — метка чернил и подпись автора в кадре доски; чем опасна «догоняющая» запись

**Метка «<имя> нарисовал(а), показать».** Учителю важно не только то, что ученик рисует, но и то,
ЧЕЙ кадр приехал: раньше `type: 'edits'` не содержал автора, и узнать его клиент мог только опросом
счётчиков (`GET /api/lessons/:id/board/authors`) — то есть HTTP-запросом на каждый кадр, что прямо
противоречит решению части 3 (не удваивать трафик урока). Сервер теперь кладёт в кадр `by` —
идентификатор отправителя ИЗ ИДЕНТИЧНОСТИ СОКЕТА (его же ставит `gateEdits`), а не поле из тела
сообщения. На права `by` не влияет: это подпись у уже принятых сервером элементов. Отсюда правило:
подпись автора едет вместе с кадром, а не выводится на клиенте эвристиками.

**Отличать чужой КАДР от чужой СТРАНИЦЫ.** 'current' и 'pages' — это вся доска (переключение
вкладки учителем, поздний вход ученика). Если реагировать на них, плашка «нарисовал(а), показать»
вспыхивала бы на каждое переключение; метка зовётся только по 'edits' и только по элементам, которых
у учителя раньше не было (`knownRef`).

**Что дороже любого «улучшения»: ветка «догнать документ накопленным значением» в
`controlledEditor` убила хвост каждой порции печати — это поймал собственный тест zz24 на CI
(прогон `38795245220`, CPU ×4): `альфаbravo012чарлиdelta987654…` вместо `…0123456789…3210…`.
Причина: во время печати документ по праву опережает последнюю отдачу (ProseMirror дочитывает DOM
следующим наблюдателем), и запись `pending` в такой момент стирает ещё не зафиксированные символы.
Догонять можно только по реальной СМЕНЕ экземпляра редактора — это единственный случай, когда
документ собран из старого `value`. Правило: любая обратная запись в редактор должна быть привязана
к событию, которое её оправдывает (смена документа, смена экземпляра, потеря фокуса), а не к
расхождению значений..

## 2026-10-16 — урок живёт над роутером (портал вместо переноса состояния)

**Что решено.** Комната, сокет урока, комментарии, руки, устройства, лекция и показ экрана
монтируются `LessonHostProvider` (apps/web/src/components/LessonLive.tsx) НАД `<Routes>`.
Страница `/lesson` больше не элемент маршрута, а слот: `LessonSlot` регистрирует свой DOM-узел,
а компонент урока рендерит туда разметку через `createPortal`. Уход на другую страницу снимает
слот — и тот же экземпляр урока переежает порталом в мини-окно. Состояние не пересоздаётся,
`room.connect` не вызывается второй раз, второй участник не появляется.

**Почему так, а не «состояние в контекст».** Требование владельца — «страница урока только
рендерит». Прямая перенос ~1300 строк из `pages/Lesson.tsx` в хук — это переписывание логики
лекции, возврата устройств, эпизодов и снимков, которые правились red-гонами несколько недель
подряд и проверяются только RTC-спеками. Проверяемый locally результат такого переноса — только
typecheck; браузерные тесты локально не запускаются по тому же новому порядку. Портал даёт те же
гарантии (одно подключение, переход не рвёт урок, мини-окно видит те же данные) при нулевом
переносе логики: переезжает DOM, а не состояние. Честная формулировка для отчёта: *провайдер
владеет экземпляром урока; состояние урока не вынесено в контекст приложения*.

**Выключатель.** `LESSON_PERSIST` (по умолчанию вкл.) отдаётся наружу через `GET /api/features`
и читается SPA до монтирования урока. При `off` хост монтирует урок ровно пока открыт маршрут
`/lesson` — то есть прежнее поведение байт-в-байт, и откат не требует сборки.

**Метка возврата** живёт в `sessionStorage` (`blublu.rejoin`: идентификатор урока, класс/событие,
время; секретов нет), срок 2 минуты. Пишется ПОСЛЕ успешного входа и снимается при выходе.
Парная проверка к ней в zz25 обязательна: assertion «плашки нет» без assertions «плашка есть»
проходит пусто — на этом ровно так и прятался дефект метки чернил (`0103bbe`).

## 2026-10-16 — часть E: редактор текста наконец отдал право на текст документу

**Что решено.** `controlledEditor.ts` удалён, вместо него `uncontrolledEditor.ts`
(`useDraftEditor`) и чистые правила в `packages/shared/src/editorDraft.ts`. Текстовый редактор
болен не гонкой, а схемой: пока значение из состояния страницы может быть записано в документ,
найдётся момент, когда документ опережает это значение, и обратная запись сотрёт набранное.
Шаг 19 уже сузил окно (не писать, пока в фокусе) и отдельную ветку «догнать» оставил — хвост
печати под CPU ×4 пропал именно там. Теперь ветки «догнать» нет вовсе: запись снаружи бывает
только при первом монтировании, при смене идентификатора документа и по явной кнопке.

**Правила, из которых это следует.**
1. Несохранённое живёт в локальном черновике (`klass.draft.<область>.<документ>`, срок неделя),
   а не в надежде, что дебаунс успеет до `pagehide`.
2. Победивший черновик обязан быть отдан родителю. Иначе получается поле, которое показывает
   учителю один текст, а публикует другой — это и есть потеря, только невидимая.
3. Черновик убирает страница и по тому значению, которое ОНА ОТДАЛА на сервер, а не по ответу
   сервера: санитайзер вправе переписать разметку, и «равно ответу» перестало бы означать
   «сохранено».
4. Идентичность ещё не созданной заметки постоянна (`__draft__`), а ключ экземпляра редактора
   и ключ черновика — разные параметры хука (`docId` и `draftId`). Иначе ненабранный текст новой
   заметки нечего было бы прочитать после перезагрузки, а перенос ключа при POST (`moveDraft`)
   стал бы гонкой с последним нажатием.
5. Подсказка с действием не прячется по таймеру. Прятать кнопку «вернуть локальный черновик»,
   пока человек её читает, — тот же класс потери данных, только вежливый.

## 2026-10-16 — часть F: почта включается одним провайдером, и требование кода — свойство транспорта

**Что решено.** Подтверждение адреса включается ровно одной переменной `EMAIL_PROVIDER`
(по умолчанию `none`) и второго выключателя нет намеренно: «письма ходят», «регистрация требует
код» и «SPA показывает поле кода» — одно и то же состояние, а три переменные неизбежно разъехались
бы наполовину настроенным деплоем. Требование кода в маршрутах берётся из внедрённого
`EmailTransport` (`provider !== 'none'`), а не из `env`: тест подставляет консольный транспорт и
получает настоящий тракт без подмены окружения, а живой процесс — то, что настроил владелец.

**Почему код спрашивается после имени и фамилии.** Чтобы письмо обращалось к человеку по имени, а не
было машинной строкой. Побочный эффект тот же: у поля «Фамилия» появляется экранирование, иначе
введённое в форму имя становится HTML письма (и это была бы дыра, а не косметика).

**Что дороже красивого кода: попытка не должна жить в транзакции.** Первое решение было «одним
махом»: списать код внутри транзакции регистрации и там же увеличить счётчик неверных попыток —
красиво, один путь, никаких состояний. Тест покраснил его дважды: (1) попытка, записанная внутри
транзакции, уезжала вместе с откатом (не тот код класса → откат → счётчик снова ноль), то есть
потолок из пяти попыток был бесплатным для переборщика; (2) в самом списании потолок не
проверялся, и верный код проходил после пяти ошибок. Теперь проверка (`precheckEmailCode`, попытка
пишется отдельным не откатываемым ходом) и списание (`consumeEmailCode`, один `UPDATE … RETURNING`
внутри транзакции) — это два разных утверждения про два разных отказа: неверный код стоит попытки,
а отказ по коду класса попытку не сжигает и оставляет письмо живым. Правило: **всё, что должно
пережить откат, обязано писаться ДО транзакции; всё, что должно откатываться, — внутри.**

**Ответ не раскрывает существование почты** — ровно одно место, где это возможно: `/api/auth/email-code`
отвечает `202 {ok:true}` и когда письмо ушло, и когда адрес занят (письма тогда нет). Различить
ветки можно, только владея ящиком. Отдельные ответы — `429 emailCooldown` и `503 emailUnavailable` —
говорят о скорости и о провайдере, то есть о сервере, а не о наличии аккаунта. Существующие
пользователи не блокируются по построению: аккаунт создаётся только после верного кода, колонки
«подтверждён» в `users` нет, и вход ничего не проверяет — поэтому ни один существующий аккаунт
нельзя закрыть новой проверкой.

**SMTP без новой зависимости.** `pnpm audit` — блокирующий шаг CI (часть C4), и каждый пакет в
`dependencies` это чужой код, который CI обязан переживать; разговор SMTP короткий
(EHLO → STARTTLS → AUTH LOGIN → MAIL FROM → RCPT TO → DATA → QUIT), поэтому он свой, в одном файле,
и проверяется настоящей TCP-куклой, а не mock'ом самого себя. Отказ — короткая `SmtpError` без
пароля и без тела письма. `security: 'starttls'` при сервере без STARTTLS падает, а не молча
уходит в открытый текст: тихий fallback и есть та «безопасность, которая выключается сама».

## 2026-10-16 — часть G: кадры телефона это артефакт, а не утверждение

**Чем кадры лучше проверки.** `m-phone-screens` спрашивает геометрией: горизонтального скролла
нет, полоса не накрыта, цели ≥ 44 px. Этот набор утверждений не может поймать «подпись легла в
две строки и сдвинула таблицу» или «тёмная тема забыла фон карточки» — прямоугольники у обоих
дефектов правильные. Пиксельный эталон не выбран сознательно: он умирает на каждой смене шрифта
и превращает набор в список разрешённых отличий. Поэтому съёмка ничего не утверждает про вёрстку
и утверждает только то, что кадр годен для просмотра: экран отрисовался, `documentElement.lang`
равен снимаемому языку, `html[data-theme]` равен теме из имени файла.

**Почему отдельный неблокирующий джоб, а не ещё один assert внутри e2e.** 60 PNG и ~60 переходов
страниц — это десять минут к набору, который и так упирается в таймаут (прогон 38506706395 сняли
таймером на 25m21s), и ни одной новой гарантии. Спек помечен `@shots`, блокирующий `e2e` запускается
`--grep-invert "@unstable|@shots"`, и его состав не изменился (110 тестов и до, и после). Ни один
тест не удалён и не ослаблен: у съёмки просто свой джоб с `continue-on-error: true`, как у
`@unstable`, и артефакт грузится с `if: always()` — оборванный прогон обязан показать, на каком
экране он оборвался.

**Стрелка устройства стала целью в 44 px, и заодно полоса — уже.** `mic-toggle-menu`
(`.bar-arrow`) имел `min-width: 28px`, из-за чего строгая проверка 44 px на уроке была красной.
Прятать стрелку на телефоне нельзя — на ней выбор микрофона/камеры, который держат zz17/zz18.
При 44 px восемь целей полосы дают 352 px, а коробка полосы на 393 px равна 377 px (правело
`left: 8 / right: 8`), поэтому с прежними зазорами (gap 4 × 5 + padding 10 × 2 + границы 2 = 42)
полоса вышла бы за экран. В `@media (max-width: 767px)` зазор 2 px и отступы 4 px — итог 372 px,
5 px запаса. Числа оставлены комментарием в CSS: без них следующая правка «на глаз» вернёт
переполнение, и ловить его придётся снова красным прогоном.

## 2026-10-17 — заход A–E: порядок языков, поля даты, свёрнутая рейка, центр полосы, Word с текстом

**A. Порядок языков — своя константа, а не перестановка `SUPPORTED_LOCALES`.** Требование «один
источник порядка» формально выполнялось и тем, чтобы перевернуть `SUPPORTED_LOCALES` в shared. Не
сделано: этот массив — домен валидации, из него собираются `z.enum` в `schemas.ts` и порядок значений
в `pgEnum('app_locale', …)`, и трогать его ради того, что видит человек, означало бы рисковать
миграцией и подписями ради косметики. Поэтому рядом лежит `LANGUAGE_CHOICES` (код + родная подпись,
порядок uz → en → ru), а паритет с `SUPPORTED_LOCALES` держит юнит-тест: добавить четвёртый язык и
забыть его в меню теперь нельзя. Значение по умолчанию осталось `en`: первая строка меню — это
видимость, а не фолбэк, и тест это прямо утверждает.

**Почему кнопки `/language` в боте не переупорядочены.** Постановка перечисляет экраны приложения
(сайдбар, мобильная полоса и меню, вход, регистрация, профиль). Telegram-клавиатура — другая
поверхность, и её порядок в этом заходе не менялся бы «вне задачи»; это названо в отчёте, а не
проигнорировано молча.

**B. Свой календарь, а не `react-day-picker`.** Библиотека была разрешена «при необходимости», и
необходимости не оказалось: нужен один месяц с понедельника, названия из `Intl` и размещение на уже
существующем `lib/popover.ts`. Свой грид — 60 строк в компоненте и ни одной новой зависимости в
браузере; чанк `DateTimeField` — 6,82 kB (2,83 kB gzip). Разбор и форматирование вынесены в
`@klass/shared/dateTimeField` как ЧИСТЫЕ функции: это единственное, что даёт проверить три языка и
неверные значения без браузера, а браузерные спеки локально запрещены.

**Значение поля не изменилось, и разбор принимает канонический порядок.** Нативный
`datetime-local` хранил `YYYY-MM-DDTHH:mm`, и этим же значением кормят форму `toLocalInput()` и
автоматизация (`flow`, `redesign`, `material`). Если бы принимался только человекочеевый вид
`дд.мм.гггг чч:мм`, правка стала бы ломкой: серверный трафик остался бы тем же, но сломались бы
три спека и две функции-источника. Поэтому поле показывает язык интерфейса, а внутрь отдаёт то же
значение, и дополнительно понимает ISO-запись. Неверное значение даёт `''` — то есть ровно то же,
что пустое поле, а обязанность заполнять поле решает вызывающий код (в форме события это `disabled`
на кнопке сохранения).

**C. Вылет меню считается от рейки, а не от кнопки.** Первая версия ставила меню в 4 px от правого
края КНОПКИ; кнопка стоит внутри рейки (padding 8 + 47 ширины), и меню на 5 px перекрывало саму
панель — то есть «выход за рамку» только переехал. Якорем в свёрнутом режиме стала рейка: отсчёт идёт
от её края, клик по кнопке меню закрывает по-прежнему своим `onClick`, клик мимо панели — общий
механизм. Общий `popPos` получил вариант `align: 'right'` (низ меню прижат к низу якоря, координаты
клампятся к вьюпорту с учётом прижатых к краям полос) — вместо четвёртой по счёту ручной посстановки
меню, которая и была первопричиной аудита шага 9.

**Инлайн-стили убраны там, где они перебивали правила панели.** `justify-content: flex-start` и
`padding: 16px` у кнопки раскрытия, `padding: 4px 8px` у `.side-lang` — инлайн всегда выигрывает у
класса, поэтому правила свёрнутого состояния их не видели бы.

**D. Центр полосы урока — одна CSS-переменная, а не `left/right`.** Соблазн был задать
`left: var(--scene-left); right: var(--scene-right); margin-inline: auto`, и он ломается на
узких поясах: при `width: fit-content` и обоих краях свободное место распределяется только когда
полоса уже пояса, а на 1024 px с открытой правой панелью она шире — и полоса прижималась бы к левому
краю пояса. Поэтому пишется ОДНА величина (центр пояса), а полоса ставится в неё через
`transform: translateX(-50%)`: перекос пояса симметричен, и полоса не уходит за экран. Правило
автоскрытия переведено на `translate(-50%, …)` — иначе `translateY` затирал бы горизонтальный сдвиг.

**Колбэк-реф вместо чужого ref.** `.lesson-main` появляется не в первом рендере (загрузка урока,
экран входа в комнату). Effect, однократно прочитавший `ref.current`, на пустом месте не наблюдал бы
ничего и молча оставил бы прежнюю центровку; хук поэтому отдаёт колбэк-реф и переподписывается, когда
элемент появляется.

**E. `.docx`-сборка переехала в shared, потому что тестам без браузера нужен тот же код.**
`apps/api` не видит зависимости `apps/web` (pnpm изолирует `docx` в `apps/web/node_modules`), а
проверять «собери и распакуй» надо именно там, где уже живут юниты. Решение — `docx` в зависимостях
`@klass/shared` и отдельный под-путь `@klass/shared/boardDocxBuild`, НЕ через `index.ts`: иначе
статический `import from '@klass/shared'` затянул бы библиотеку в начальный чанк. Внутри сборщика
загрузка осталась динамической, и это проверено: `w:document` встречается ровно в одном чанке
сборки, 408,44 kB (118,58 kB gzip) — как и было до переезда.

**Подложка тоже живёт в рамке — и это осознанная лишняя рамка.** Рамка страницы считается от
bounding box ВСЕХ элементов, иначе текст, торчащий за фигуру, терялся бы за листом. Значит у самой
картинки тоже должен быть сдвиг (фигура может не начинаться от левого края доски), а позиционировать
её иначе, чем `w:framePr`, нечем. Поэтому в редактируемом режиме рамок на одну больше, чем текстов, и
тест называет это число прямо.

**Пустой текст не идёт ни в подложку, ни в строки.** Element с `text: ''` ничего не рисует, но
попадал бы в рамку доски и портил масштаб. Повёрнутый текст остаётся в подложке: `w:framePr` не
умеет поворот, и честнее оставить его картинкой, чем молча развернуть.

**Один масштаб вверх — потолок 3×.** Иначе доска из одного слова растянулась бы на кегль в сотни
пунктов. Потолок не противоречит «масштабировать большие»: он ограничивает только увеличение.

**Что остаётся непроверенным.** Автоматизация видит XML: число рамок, побуквенное совпадение текста,
одну картинку на страницу и рамки внутри листа. Что Word и LibreOffice покажут эти рамки ТАМ ЖЕ, где
их оставил человек, — вопрос живого редактора, и это §8 в docs/MANUAL_QA.md. Ожидаемые расхождения
названы заранее: Word заменит шрифт на системный Arial, строки могут сместиться на полстроки из-за
межстрочного интервала, а Excalidraw считает границу элемента по своим отступам, и если её bounding
box окажется больше нашего, подложка уедет на несколько точек.

## 2026-10-23 — часть B: вход и регистрация всего класса с одного адреса

**Причина общей ошибки на шаге 2 найдена по коду, а не по догадке, и она реальна.**
`registerStudentByCode` превращал занятый адрес в `emailTaken` по проверке `err.code === '23505'`.
Вне транзакции это работало, внутри — нет: drizzle-orm (0.45.3) оборачивает ошибку драйвера в
собственный `Failed query: …`, и Postgres-код остаётся только на `err.cause.code`. Воспроизведение
(вторая регистрация занятого адреса) дало `500` и в логе Поста —
`duplicate key value violates unique constraint "users_email_unique"`; интерфейс на 500 говорит
ровно одну нейтральную фразу, «Something went wrong. Please try again.». Это ровно тот симптом,
который описывала ученица, уже состоящая в списке класса. Исправление двуслойное, и оба слоя нужны:
обычный случай читается ЯВНО (`SELECT id FROM users WHERE email = …` внутри той же транзакции, без
фильтра по `deleted_at` — уникальный индекс тоже не различает удалённых), а гонка двух одновременных
регистраций одного адреса по-прежнему решает уникальный индекс, для него обход цепочки `cause`
доходит до конца. Тест: `test/integration/auth-nat.test.ts` требует 409, `used_at IS NULL` у второго
кода и ровно одну строку `users`.

**Регистрация атомарна была и остаётся — теперь это проверено, а не заявлено.** Списание кода
класса, вставка аккаунта, вставка членства и списание кода из письма идут одним ходом транзакции,
поэтому сбой шага 2 не «сжигает» код и не оставляет аккаунт без членства. Отдельный тест на это
был нужен именно потому, что первая причина живёт в том же коде: легко было «починить» 409 ценой
разноса транзакции на два шага.

**Второй источник «не могут заходить» — лимит на здание.** Логин был ограничен 10 попытками в минуту
НА IP, кодовые маршруты — 8, и 11-й ученик школьного Wi-Fi (или 30 телефонов за одним NAT
провайдера) получал 429 от `@fastify/rate-limit` с телом `{error: "Too Many Requests"}`. Это НЕ код
интерфейса, поэтому перевод найти было нечем, и экран показывал ту же общую ошибку, что и упавший
сервер. Теперь два разных слоя, и путать их нельзя:

  • **потолок потока по адресу** — 120 запросов / 10 минут на каждый auth-маршрут
    (`PROD_IP_WINDOW_MAX`, env `RATE_IP_MAX`); наружу — `tooManyRequests` + `retry-after`;
  • **защита от перебора по признаку** — `(IP + код)` 8 неудач/мин, `(IP + почта)` вход 10 неудач/мин,
    `(IP + почта)` регистрация 5 попыток/мин, и `af:<IP>` 20 неудач ЛЮБОГО рода/мин (вне прода —
    500, потому что тесты подбирают пароли намеренно), после чего этот ключ блокируется на 15 минут;
  • **перебор по аккаунту не тронут** — прогрессивный Postgres-лок: 5 подряд → 30 с, далее ×2,
    потолок 15 минут. Успехи не увеличивают ни один счётчик неудач.

**Арифметика вместо «сделаем щедрее».** Реальный класс принят в 30 человек; запросов на ученика в
худшую «минуту входа» — 3 (проверка кода + регистрация, или вход + перепечатанный пароль) ⇒ 90 запросов;
120 — это +33 % запаса, и при этом 1 запрос на каждые 5 секунд, минут за десять подряд: честному
человеку столько не нужно. Чтобы выработать этот же бюджет своими действиями, одному ученику пришлось
бы 40 раз успешно войти — это уже поток, а не вход на урок. Перебор же ограничен в 6–12 раз более
узкими окнами по признаку, и он не меняется от того, что адрес стал щедрее.

**У каждого отказа есть переводимый код и reqId.** Словарь кодов живёт в
`packages/shared/src/authErrors.ts`, и юнит `test/unit/auth-messages.test.ts` требует, чтобы у КАЖДОГО
из них была фраза в ru/uz/en (длиннее 12 символов), а любое тело с незнакомой строкой (например, текст
драйвера или библиотеки) складывалось в `invalidInput` — то есть «Too Many Requests» больше не может
просочиться наружу. Под фразой экран печатает 10-символьный `reqId` (алфавит без `i l o u 0 1`,
чтобы его можно было продиктовать по телефону), он же — в заголовке `x-request-id` и в access-логе
(`reqId`), так что «у меня ошибка abc123xyzw» превращается в одну строку в журнале. Формулировка
занятого адреса намеренно условная («если вы уже регистрировались…») и не утверждает, что аккаунт
существует; рядом — кнопка входа.

**`browserContext` переехал в shared, и сделался честным.** Подсказка «откройте в настоящем
браузере» должна срабатывать только там, где куки действительно не выживают, а
`navigator.cookieEnabled` врёт в нескольких приватных режимах — значит надо писать и читать пробную
куку. Первая версия принимала строку `document.cookie`, прочитанную ДО записи, и потому в WebView
никогда не видела работающего банка (это поймал юнит-тест: `expected true to be false`). Теперь функция
получает `read`/`write` извне и остаётся чистой — то есть проверяемой без браузера, чего `apps/web`
сделать не может (там нет юнит-раннера, только `typecheck` и `build`).

**Изменённые существующие тесты — и почему это не ослабление.** `registration.test.ts` («коды
неверен/использован/истёк неотличимы») и `email-verification.test.ts` (ответ без кода из письма)
сверяли тело равенством `toEqual`; теперь они сверяют код, форму `reqId` и — для неотличимости —
ВСЁ тело, кроме `reqId`, что строго сильнее прежнего: различать три состояния кода по-прежнему нечем.
`phase2-lockout.test.ts` («заблокированный аккаунт и несуществующий адрес») то же самое: сравнение
по телу без id, плюс проверка, что id разные. `access-log.test.ts` требовал `{error:"serverError"}`
ровно одним объектом — теперь он требует тот же код, правильный `reqId` и РОВНО тот же id, что
лежит в журнальной строке, то есть связывает две половины контракта. `rate-limit.test.ts` бьёт по
окну признака (одна почта), а не по адресу, — иначе он проверял бы не то, что в нём заявлено.
`prod-config.test.ts` измеряет производственную матрицу двумя проверками вместо одной: 12 неудачных
входов одной почты (жёсткий потолок 10/мин, `RATE_LOGIN_MAX=10000` проигнорирован) и 122 запроса с
одного адреса разными почтами (120/10 мин, `RATE_IP_MAX=100000` проигнорирован).

**Новые переменные окружения.** `RATE_IP_MAX` (по умолчанию 120) и `RATE_IP_FAIL_MAX` (20) — обе
действуют только вне production, где значения взяты из кода и relaxation из env не читается.

**Что осталось непроверенным без живых устройств.** Здесь нет ни школьного NAT, ни настоящего
Telegram WebView: адреса подставлены `inject`-ом, банк cookies — симуляцией, а подсказка «открыть в
браузере» — юнитом. Сколько учеников в реальном классе, какой у них провайдер и что они увидят на
шаге 2 после починки — проверяется руками: §12 в `docs/MANUAL_QA.md`.

## 2026-10-23 — часть A: панель стилей доски открывается по кнопке, а не сама

**Рычаг искали по документации установленной версии, а не на глаз.** Прочитано из
`node_modules/@excalidraw/excalidraw` (0.18.1, типы в `dist/types/excalidraw/types.d.ts`):
`UIOptions` = `dockedSidebarBreakpoint` + `canvasActions` + `tools.image` — записи про панель
стилей НЕТ, и ни один пропс `ExcalidrawProps` её не прячет (рядом только `renderToolbar`,
`renderTopRightZone` и т.п., которые рисуют ЧУЖУю панель вместо штатной). Единственное поле
состояния, которое выглядит как выключатель, — `appState.openMenu: 'canvas' | 'shape' | null`.

**Почему `openMenu` не стал решением.** В собранном коде десктопного меню панель рисуется так:
`O = fi(appState, elements)` и далее `children: [M(), O && N()]`, где `N()` — островок
`heading: "selectedShapeActions"`, `className: "selected-shape-actions …"`. То есть на широком
экране видимость решает предикат «есть чего показать», а не `openMenu`. Тот же `openMenu === "shape"`
встречается только в мобильной ветке (`App-bottom-bar`). Оставить кнопку, которая пишет в это поле,
значило бы оставить интерфейс, где `aria-pressed` спорит с тем, что человек видит.

**Поэтому состояние наше, и оно одно.** `data-styles="open|closed"` на `.board-frame` + CSS-правило
`display:none !important` по классу контейнера панели — и десктопного (`.selected-shape-actions`), и
мобильного (`.App-mobile-menu`). Кнопка, `aria-pressed` и правило читают ОДНО булево, так что
расхождение невозможно по построению. Это ровно та «запасная» ветка, которую ставил приоритет
«пропсы → иначе CSS по устойчивому классу», и она выбрана не ленью, а потому что первой ветки нет.

**Правило «класс исчезнет» проверено в обе стороны.** Новый юнит
`test/unit/excalidraw-styles-panel.test.ts` читает УСТАНОВЛЕННУЮ библиотеку: класс обязан остаться в
JS-бандле, обязан сидеть рядом с заголовком `selectedShapeActions` (расстояние ≤ 400 символов —
переименование переменных минификатором на соседство не влияет) и обязан называться в нашем
`styles.css` тем же именем. Негативный контроль прогоняли реально: первая версия проверки НЕ упала
на переименованном классе (регэксп ловил префикс `.selected-shape-actions` внутри
`.selected-shape-actionsX`) — после этого в селектор добавлена граница имени `(?![\w-])`, и тот же
контроль теперь падает.

**Память — раздельная по роли, и узкое окно ничего не портит.** Ключ `blublu.board.styles.teacher`
против `blublu.board.styles.student`: ученику выдали право рисовать на середине урока — его выбор не
должен перетекать в учительский и наоборот. При ширине < 1280 px панель закрыта, но сохранённый
выбор НЕ перезаписывается: расширил окно — вернулся тот же режим, что был. Правила живут в
`@klass/shared/boardStylesPanel.ts` как чистые функции — у `apps/web` нет юнит-раннера, а браузерные
спеки локальны forbidden, поэтому «закрыто по умолчанию» и «390 px» доказываются юнитом
(`test/unit/board-styles-panel.test.ts`), а не скриншотом.

**Крестика ВНУТРИ панели не делал.** DOM острова стилей принадлежит Excalidraw и слота для чужой
кнопки у него нет, а вставлять узел в чужой контейнер — значит потерять его при первом же
перерендере библиотеки. Закрывают: та же кнопка шапки (открытая панель показывает на ней ✕) и Esc.
Про крестик прямо спрашивать нужно руками — §13 в `docs/MANUAL_QA.md`.

**Мелочи, которые стоят отдельно.** Глиф кнопки лежит в ячейке фиксированной ширины: 🎨 и ✕ разные
по ширине, шапка доски — flex с переносом, и без фиксированной ячейки нажатие кнопки сдвигало бы
полотно на пиксель-другой ровно в момент, когда человек целится мышью. Esc не делает
`preventDefault`: полотно обрабатывает Esc само (снять рисование), и горячие клавиши инструментов
обязаны продолжать работать при закрытой панели. Фокус возвращается на кнопку ТОЛЬКО если он был
внутри панели — иначе клавиатура холста переезжала бы на кнопку после каждой отмены.

**Что осталось непроверенным.** Что панель реально исчезает на экране, что цвет и толщина доступны
после нажатия кнопки, как ведёт себя полотно на 390 px и в тёмной теме — всё это видно только в
живом браузере; автоматизация здесь доказывает лишь связку «класс библиотеки ↔ наше правило ↔ наше
состояние».

**Что поймал первый CI-цикл этой правки (прогон 39993977646), и почему исправлен код, а не спек.**
`zz20-board-students` требует, чтобы выдача права рисования НЕ двигала полотно (допуск 2 px). В
первой версии кнопка «Стили» появлялась в шапке ученика только вместе с правом — и строка шапки
вырастала на 10,25 px ровно в момент выдачи (разница между высотой pill-ячейки 36 px и высотой
кнопки 44 px), то есть полотно уезжало вниз. Спек прав: это именно тот класс дефекта, против
которого в этом файле уже стоит резерв высоты ячейки состояния. Исправление — кнопка рендерится
всегда и при отсутствии права просто выключена с объяснением в подсказке, а `.board-status`
переведён на `min-height: var(--tap)`; место зарезервировано в обоих состояниях, сдвиг нулевой.
Мёртвой кнопки тут нет: выключено то, что нельзя использовать по правам, а не то, что никогда не
работает в этом браузере (ср. шаг B1 про `getDisplayMedia` на телефоне).

## 2026-10-23 — часть C: окно показа экрана поверх других программ

**Рычаг один, и он не `window.open`.** `documentPictureInPicture.requestWindow()` — единственный
способ дать странице окно поверх других программ; popup-вкладка для этого не годится (она живёт
внутри браузера и зовёт блокировщик всплывающих окон). API открывается ТОЛЬКО из пользовательского
жеста, поэтому запрос стоит ДО публикации дорожки и запущен синхронно в том же нажатии, что и
«Демонстрация экрана» (`toggleShare` вызывает `openShareWindow()` до первого `await`).

**Чем это рискует и почему риск принят.** Жест один, а API требуют его оба:
`requestWindow` и `getDisplayMedia`. Порядок «окно → показ» выбран сознательно: если браузер
заберёт активацию у второго вызова, показ не случится, и код это лечит — при отказе публикации
окно закрывается, а человек видит прежнюю `screenShareFailed`. Обратно хуже не получается: при
порядке «показ → окно» окно пришлось бы просить вне жеста, то есть всегда проигрышно. Поэтому в
плашке показа и в «Ещё» живёт отдельная кнопка «Вынести окно» — то же окно, запрошенное своим
нажатием, и она же остаётся единственным путём, если первый порядок не сработает. Это первый пункт
живой проверки (§14 в docs/MANUAL_QA.md).

**Второго соединения к LiveKit нет.** Окно — портал из того же дерева React
(`createPortal(<SharePip/>, pipWindow.document.body)`), и `track.attach()` вешает ТУ ЖЕ дорожку
комнаты на второй `<video>` в другом документе. Права, токены и серверная часть не тронуты: окно
ничего не публикует и не запрашивает, оно показывает то, что уже публикуется. Ученики видят урок
ровно как раньше — изменится только экран показывающего.

**Пустой документ окна надо одеть руками.** `documentPictureInPicture` даёт чистый документ,
поэтому в него переносятся: все `<link rel=stylesheet>` и `<style>` в исходном порядке (порядок
важен — иначе переопределения в `styles.css` поедут), относительные `href` абсолютятся от основной
страницы (своей базы у окна нет, и `/assets/x.css` ушёл бы в `about:blank`), `data-theme` с
`<html>` (иначе тёмный урок открывает светлое окно) и `lang`/`dir`. Отдельно абсолютятся `url(...)`
внутри инлайновых `<style>`: в dev-режиме Vite вкладывает CSS именно так, а `/fonts/*.woff2` из
`fonts.css` — наша self-hosted подписка на `oʻ`/`gʻ`); без этого окно в dev вышло бы системным
шрифтом, и «шрифты едут вместе с CSS» было бы верно только для сборки. `data:`, `blob:`, `http(s):`
и `//host` не переписываются: неудачная попытка испортила бы inline-шрифт. Отказ перенести стили
показ не роняет — окно остаётся рабочим, просто без темы.

**«Коридор зеркал» решён по поверхности — но только в НОВОМ окне.** Уже было: `selfBrowserSurface:
'exclude'` в ограничениях показа и предупреждение, когда человек всё-таки выбрал свою вкладку
(`displaySurface === 'browser'`). В окне показа правило такое: весь монитор — предпросмотр свёрнут
(его человек видит и так), окно/вкладка — показан, неизвестная поверхность — показан (в отдельном
окне пустая область хуже лишней плитки). Переключатель рядом, потому что выбор человека важнее
правила.

**Именно здесь меня поймал первый CI-цикл (прогон 39993977646), и чинил я код, а не спек.** Первая
версия правки распространила это правило ещё и на предпросмотр В ПЛАШКЕ УРОКА (`share-preview`), а
там с task 1.3 намеренно лежит «свёрнут по умолчанию, разворачивается по кнопке», и это пинает
блокирующий `zz13-screen-stage` (`toHaveClass(/preview-min/`). Спек поймал законную ошибку: моя
догадка про неизвестную поверхность молча меняла зафиксированное поведение урока. Поведение
плашки возвращено к прежнему (свёрнут для любой поверхности), а правило поверхности осталось там,
куда его просила постановка, — в окне. В коде это теперь написано текстом, чтобы правка не
повторилась (`previewOpenByDefault` в `@klass/shared/screenPip.ts`).

**Где окна нет — не мёртвая кнопка.** Решение по факту наличия API (`'documentPictureInPicture' in
window`), а не по строке UA; UA используется только чтобы ОТказаться на телефоне, где такое окно
бесполезно. В Safari/Firefox показ работает как раньше (плашка с «Остановить» + внутреннее
мини-окно), и один раз появляется строка «откройте урок в Chrome или Edge» с кнопкой «Больше не
показывать» — после закрытия она не возвращается (`blublu.lesson.pipHintOff`).

**Автоматизация: юниты + один @unstable спек.** Четыре решения, которые принимаются ДО вызова API,
вынесены в `@klass/shared/screenPip.ts` и покрыты юнитами (`test/unit/screen-pip.test.ts`, 15
проверок): где окно вообще можно просить, свёрнут ли предпросмотр, когда нужна подсказка и что
именно переносится в пустый документ (включая абсолютные `url()` для инлайновых `<style>`). Спек `apps/e2e/tests/zz28-screen-pip.spec.ts` помечен
`@unstable` и уехал в неблокирующий джоб по честной причине: увидит ли Playwright окно Document
PiP среди страниц контекста — неизвестно (у него свой top-level контекст), а проверка требует живую
комнату. Спек сам себя пропускает с названной причиной и падает только тогда, когда API есть, окно
открылось, а содержимого нет. Ручные шаги — §14 в docs/MANUAL_QA.md; без реального компьютера здесь
не доказать ничего вообще: ни что окно лежит поверх Word, ни что видео внутри него рисуется.

**Что НЕ сделано из постановки.** Окно 360×220 задано старым размером; «resizeable» у Document PiP
включать нечем — окно ресайзится само. Никаких прав, токенов и серверных маршрутов часть C не
касается, и это проверено диффом: изменены только `apps/web` и `packages/shared`.
