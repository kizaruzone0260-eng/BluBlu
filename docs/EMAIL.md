# Почта: подтверждение адреса при регистрации

Часть F (2026-10-16). Единственный включатель — `EMAIL_PROVIDER`. При `none` (значение по
умолчанию) письма не ходят, маршрутов подтверждения не видно, а регистрация остаётся ровно
прежней — байт-в-байт, включая ответы `409 emailTaken`. Поэтому включение этой функции не может
сломать живой деплой, где почту не настроили.

## Как это выглядит для человека

1. Шаг 1 формы: код класса + почта + пароль (как раньше).
2. Шаг 2: имя и фамилия → кнопка «Получить код» (`POST /api/auth/email-code`).
3. Приходит письмо с шестью цифрами; в обращении — имя и фамилия, поэтому код и просится ПОСЛЕ
   того, как оба поля заполнены.
4. Шесть цифр + «Зарегистрироваться» (`POST /api/auth/register`, поле `emailCode`) — аккаунт
   создаётся тем же запросом.

SPA узнаёт о требовании из `GET /api/features` (`emailVerification: true|false`), а не из сборки:
владелец переключает поведение одной переменной в Render.

## Правила

| | |
|---|---|
| длина кода | 6 цифр, ведущие нули законны (`randomInt`, равномерно из 10⁶) |
| срок | 15 минут (`EMAIL_CODE_TTL_MS`) |
| попытки | 5 на одно письмо; шестая не принимается, даже верный код (`EMAIL_CODE_MAX_ATTEMPTS`) |
| повторное письмо | не раньше чем через 60 с на адрес (`EMAIL_RESEND_COOLDOWN_MS`) |
| перебор по IP | общий кап кодовых маршрутов (`RATE_CODE_MAX`, в проде 8/мин) + `lib/throttle.ts` |
| осиротевшая строка | убирается фоновой уборкой через сутки после истечения (`EMAIL_CODE_RETENTION_MS`) |
| в базе | только соль+SHA-256 кода (`JWT_SECRET` + адрес + код), самого кода в базе нет |

Числа живут в `packages/shared/src/emailCode.ts` и проверяются тестом; текст письма — в
`packages/shared/src/emailTemplates.ts`, там же `escapeHtml` (имя и фамилия приходят от
посетителя и попадают в HTML письма — без экранирования поле «Фамилия» было бы дырой).

## Что НЕ раскрывает ответ

`POST /api/auth/email-code` отвечает `202 {"ok":true}` и в случае «письмо отправлено», и в случае
«аккаунт с таким адресом уже есть» (тогда письмо НЕ отправляется). Различить это по ответу
нельзя; различие видно только владельцу ящика, которому письмо пришло или не пришло. Отдельные
ответы (`429 emailCooldown`, `503 emailUnavailable`) говорят о скорости и о провайдере — о
состоянии сервера, а не о наличии аккаунта.

Списание кода — внутри транзакции регистрации: не создался аккаунт (не тот код класса, занятый
адрес) → откат вместе со списанием, и человек повторяет попытку ТЕМ ЖЕ кодом. А вот неверный код
стоит попытки: она пишется ОТДЕЛЬНЫМ, не откатываемым ходом (`precheckEmailCode`), иначе потолок
в пять попыток был бы бесплатным для переборщика. Это нашёл тест, а не ревью: первый вариант
считал попытки внутри транзакции, и счётчик всегда возвращался к нулю.

## Провайдеры

| `EMAIL_PROVIDER` | что делает | что нужно |
|---|---|---|
| `none` | выключено (умолчание) | — |
| `console` | печатает одну строку в stdout с кодом и маскирует адрес (`al***@school.uz`); письма нет | — |
| `brevo` | `POST https://api.brevo.com/v3/smtp/email`, заголовок `api-key` | `BREVO_API_KEY`, `EMAIL_FROM` |
| `resend` | `POST https://api.resend.com/emails`, `Authorization: Bearer …` | `RESEND_API_KEY`, `EMAIL_FROM` |
| `smtp` | свой минимальный клиент (`apps/api/src/lib/smtp.ts`): EHLO → STARTTLS → AUTH LOGIN → MAIL FROM → RCPT TO → DATA → QUIT | `SMTP_HOST`, `EMAIL_FROM`; `SMTP_USER`+`SMTP_PASS` парой |

`smtp` выбран вместо `nodemailer` намеренно: `pnpm audit` в этом репозитории шаг блокирующий
(часть C4), и каждый новый пакет — чужой код, который CI обязан переживать. Разговор короткий,
и он проверяется настоящей TCP-куклой (`test/unit/email-code.test.ts`), а не обещанием.

Отказ провайдера: причина идёт в лог через `safeErrorMessage`, наружу — одно слово
`emailUnavailable`. Тело ответа провайдера не печатается никогда (это эхо запроса: адрес и
письмо). `EMAIL_TIMEOUT_MS` (по умолчанию 10 с) ограничивает один шаг; зависший провайдер не
держит процесс.

## Что НЕ проверено

* Живая доставка: ни одно письмо не ушло на настоящий Brevo/Resend/SMTP — проверены формат
  письма, разговор с SMTP-куклой, выбор транспорта и весь серверный тракт на записи-транспорте.
* Реакция реальных почтовых ящиков на письмо (спам-фильтры, DKIM/SPF — это зона владельца:
  без SPF/DKIM на домене школы письма с `EMAIL_FROM` уедут в спам, и ничто в коде это не проверяет).
* `security-scan` не видит `BREVO_API_KEY`/`RESEND_API_KEY`/`SMTP_PASS` в `cloud.env` (файл
  секретов владельца не читается), поэтому ключи ищутся только по форме значений в gitleaks.

## Включение

```
EMAIL_PROVIDER=brevo
EMAIL_FROM=noreply@школа.uz
EMAIL_FROM_NAME= BluBlu
BREVO_API_KEY=…
```
Плюс `render.yaml` (имена, значения не в репозитории). Половина конфигурации — ошибка старта:
процесс назовёт отсутствующие ключи и не напечатает их значения (проверено
`test/integration/boot-error-output.test.ts`).
