# Две двери Mini App: Telegram mode и Browser mode

Дата: 2026-11-04 (Task G.2). Файл описывает, как устроен запуск `/mini` после того, как
«Telegram did not load» перестал быть финальным экраном.

## Почему это отдельный документ

`Telegram did not load` появлялся в клиентах, которые ничем не похожи друг на друга: официальный
Desktop, Android, WebA/WebK в браузере, сторонние клиенты. Общий у них был не клиент, а наш код:
приложение считало наличие стороннего скрипта условием своей работы. Теперь условие работы —
сессия, а скрипт стал необязательным улучшением.

## Что проверяется до первого решения

Три независимых факта, и ни один не выводится из двух других:

| факт | где берётся | почему не вместо другого |
|---|---|---|
| состояние SDK | `ensureSdk` (`apps/web/src/lib/miniApp.ts`) | скрипт может не дойти по сети и при живом клиенте |
| наличие Telegram-моста | `telegramBridgePresent` по признакам `TelegramWebviewProxy`, `external.notify`, окно внутри `web.telegram.org` | мост дают клиенты, а не скрипт; user-agent не используется |
| наличие подписанного `initData` | `resolveLaunch` (`packages/shared/src/miniLaunch.ts`) | живой мост без подписи — не доказательство личности |

Решение принимает одна чистая функция `resolveLaunch`, покрытая таблицей истинности
(`apps/api/test/unit/mini-launch.test.ts`).

## Telegram mode

Условие: есть подписанный запуск — в `WebApp.initData` (SDK дошёл) или в адресе запуска
(`#tgWebAppData=…`, если скрипт не дошёл).

1. Клиент отправляет исходную строку на `POST /api/mini/auth`.
2. Сервер проверяет HMAC-подпись токеном бота (`lib/telegramMiniAuth.ts`), сравнивает в
   постоянное время, refuse'ит просроченную (>24 ч) и «из будущего» (>5 мин), читает Telegram id
   **только** из подписанного payload.
3. Сервер меняет подпись на ограниченный токен (`aud: blublu-mini`, `scope: mini`,
   `surface: tg`, 8 часов) и на каждом запросе сверяет живую строку `telegram_links`.

Чтение `initData` из адреса — это транспорт, а не доверие: подпись по-прежнему проверяет сервер,
`initDataUnsafe` не читается нигде, выдуманная подпись даёт 401 и ordinary вход.

## Browser mode

Условие: всё остальное — SDK не загрузился, моста нет, подписи нет, или страница открыта как
веб-дверь `/web`.

1. Экран `Sign in to BluBlu` вызывает существующий `POST /api/auth/login` (тот же
   `loginSchema`, та же защита: credential-throttle, IP-счётчик неудач, блокировка аккаунта,
   refresh-cookie `HttpOnly`).
2. Проверенный access-токен меняется на тот же ограниченный токен через
   `POST /api/mini/web/auth` — маршрут не читает тело запроса, `surface: 'web'` ставит сервер.
3. Дальше работают те же `/api/mini/*`: дом, группы, библиотека, загрузка файла, создание
   домашнего задания, AI-форматирование, публикация, история, appearance/language, документы.
   Второй реализации приложения нет.

Ничего из этого не ослабляет Telegram-дверь:

- обычный access-токен не принимается маршрутами Mini App;
- mini-токен не принимается обычным API (другой ключ подписи и `aud`);
- `web`-токен не содержит Telegram id и не может притвориться `tg`-токеном, и наоборот
  (`test/unit/telegram-mini-auth.test.ts`);
- права на группы, материалы и черновики решает сервер по `session.userId`.

## Порядок загрузки SDK

Официальный скрипт ставится в `<head>` документа `/mini` сервером
(`injectTelegramSdk` в `apps/api/src/lib/build.ts`) и выполняется раньше модуля приложения
(классический `defer` перед отложенным ESM). Никакой гонки: страница наблюдает SDK, а не создаёт
его гонку с React. Клиент делает максимум три захода (`SDK_MAX_ATTEMPTS`), повторяет только
таймаут (блокировка детерминирована) и никогда не крутится бесконечно. Веб-дверь `/web` скрипт не
просит вовсе: `bootMiniApp` с `entry === 'web'` не вызывает `ensureSdk` и не оставляет на странице
тег, который гарантированно блокируется. Договорённость записана в коде, а не вытекает из CSP —
спека `/web needs no Telegram` проверяет DOM, потому что проверка по факту сети на этом месте
оказалась холостой (замерено: блокировка происходит до запроса).

CSP: единственное расширение — `script-src 'self' https://telegram.org` на ответ `/mini`
(было и осталось). `connect-src` НЕ расширяется: скрипт грузится тегом, а не fetch'ом. `/web`,
`/`, `/login`, `/guest` получают прежнюю строгую политику без telegram.org.

## Service worker

Старый `sw.js` перехватывал все GET, включая cross-origin SDK. Worker повторял запрос от своего
имени, а CSP документа (`connect-src 'self' blob:`) подключения к telegram.org не разрешает →
запрос отклонялся, в кеше копии не было, `respondWith` получал `undefined` → `net::ERR_FAILED`.
Теперь worker не перехватывает навигации, документы и чужие домены, не кеширует HTML и не
подменяет точку входа; имя кеша поднято с `klass-shell-v1` на `klass-shell-v2`, чтобы старые
копии (в том числе HTML со строгой политикой) были удалены при activate. Цена: офлайн-рисунок
входа без сети не отрисуется (для приложения под паролем это осознанный выбор).

## Что осталось честью не сделанным

- Проверка на настоящих клиентах Telegram (Desktop, Android, WebA, WebK, Vidogram) — см.
  отчёт вне репозитория: механизм воспроизведён в Chromium, живой аккаунт владельца не тронут.
- Публичная ссылка `/web` появляется только после развёртывания: сегодня `blublu-api.onrender.com/web`
  отвечает 404 (проверено curl).
